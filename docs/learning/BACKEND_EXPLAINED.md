# VR-Nexus Backend, Explained

This document walks through the entire backend of VR-Nexus, a Tender Intelligence and Evidence Matching Platform, file by file. It is written for a final-year Computer Systems Engineering student who knows Python but has not built with FastAPI, SQLAlchemy, Celery or Redis before. The goal is twofold: understand this specific codebase well enough to extend it safely, and pick up patterns you can reuse in other full-stack projects.

## 1. What this backend does, in one request

VR-Nexus has two pipelines. The Tender Analysis pipeline takes an uploaded procurement tender (a PDF, often hundreds of pages), extracts every requirement it contains using an LLM, matches each requirement against a company's evidence library using vector search, and produces a reviewable Excel tracker plus a downloadable output folder. The Evidence Library pipeline takes a company's own documents (case studies, methodology write-ups, certificates, company profiles), parses them, splits them into chunks, embeds those chunks into vectors, and makes them searchable, both for the tender-matching step and for a "grounded Ask" feature where a user can ask a question and get an answer built only from retrieved passages, with citations.

A single request through this backend generally follows the same shape. A client (the React frontend) sends an HTTP request to a FastAPI route. FastAPI first runs the route's declared dependencies, most importantly `get_current_user`, which reads the `Authorization: Bearer <token>` header, decodes and verifies the JWT, and loads the corresponding `User` row from Postgres, rejecting the request with 401 if any of that fails. If the request carries a body, FastAPI validates it against a Pydantic schema before your route function ever sees it, so the route can assume the data is already well-shaped. The route function then talks to the database through a SQLAlchemy `Session`, which is itself provided as a dependency (`get_db`) and is closed automatically once the request finishes. For anything that takes more than a moment (parsing a 300-page tender, calling an LLM 150 times, running OCR, computing embeddings), the route does not do the work itself. It writes a row describing the job, queues a Celery task, and returns immediately, often in well under a second. A worker process, running Celery separately from the web server, picks up that task, does the slow work, and as it progresses publishes small JSON progress messages to Redis. The frontend, meanwhile, has opened a WebSocket connection (authenticated with a short-lived ticket rather than the JWT itself) that is subscribed to those Redis messages, so the browser sees the tender move through "Parsing", "Chunking", "Extracting requirements", "Matching evidence" and so on in near real time, without ever polling.

## 2. Core concepts for beginners

If you have not used any of FastAPI, SQLAlchemy, Alembic, Celery, Redis, WebSockets, JWTs or RAG before, read this section before the file-by-file walkthrough. Everything below is explained in plain terms with the goal of transferring, not just describing this one codebase.

**FastAPI path operations.** A "path operation" is just a Python function decorated with something like `@router.post("/api/tenders")` that FastAPI calls when a matching HTTP request arrives. Think of it as a named entry in a big dispatch table: the framework reads the URL and method off the incoming request, looks up which function you registered for that combination, and calls it, passing in whatever the function asked for (a validated request body, a path parameter, a database session, the current user) as ordinary Python arguments. You never manually parse the request; you declare what you want in the function signature, and FastAPI's own machinery figures out how to produce it. In this codebase every path operation lives in a module under `app/api/routes/`, each module owns one `APIRouter` with its own URL prefix, and `app/main.py` collects all of those routers onto one `FastAPI()` app.

**Pydantic schemas versus SQLAlchemy models.** These are two different jobs even though they can look similar (both are "just a class with fields"). A Pydantic schema, defined under `app/schemas/`, describes what crosses the network wire: what a request body must look like to be accepted, and what shape a response will be serialized into as JSON. A SQLAlchemy model, defined under `app/models/`, describes a row in the database: which table it lives in, which columns it has, what type each column is, how it relates to other tables. The two are kept apart on purpose. A database row can carry things a client should never see (an internal Celery task id, a raw file path on the server's disk) and a client request can carry things that never touch the database directly (a raw comma-separated keywords string that gets split into a list before storage). If you collapsed the two into one class, every change to your table would leak into your API and every change you want in your API would force a migration. Keeping them separate means the wire format and the storage format can evolve independently, and this codebase's `DocumentOut`/`Document` and `TenderOut`/`Tender` pairs are a clean example of that split in practice.

**ORM models.** ORM stands for Object-Relational Mapper. Instead of writing raw SQL strings (`INSERT INTO users (...) VALUES (...)`), you write and manipulate ordinary Python objects, and the library translates your object operations into SQL for you. `db.add(user)` followed by `db.commit()` produces an `INSERT`. `db.get(User, some_id)` produces a `SELECT ... WHERE id = ...`. Relationships between tables (a `Tender` has many `Requirement` rows) become Python attributes you can just walk (`tender.requirements`). The benefit is that your business logic reads like normal Python and the ORM keeps the SQL, the escaping, and a lot of the bookkeeping out of your way; the cost is that you need to understand roughly what SQL your ORM calls will generate, or you can write code that looks fine and performs terribly (loading a relationship one row at a time inside a loop, for instance, which is why you will see `selectinload(...)` used deliberately in a few places in this codebase to fetch related rows in one extra query instead of many).

**Dependencies (`Depends()`).** FastAPI's dependency system is its answer to "how do I share setup logic across many endpoints without copy-pasting it into every function." You write a small function, say `get_current_user(credentials = Depends(bearer_scheme), db = Depends(get_db))`, and then any route that needs an authenticated user just declares `current_user: User = Depends(get_current_user)` as a parameter. FastAPI notices the `Depends(...)`, runs the dependency function first (which itself has its own dependencies, resolved first), and only calls your route once every dependency has succeeded. If a dependency raises an `HTTPException`, your route body never runs at all and the client gets that error. This is how VR-Nexus enforces "every protected route requires a valid access token" and "some routes additionally require the admin role" without writing an authentication check by hand in eighty different functions; `app/api/deps.py` defines `get_current_user` and `require_role(...)` once, and every route that needs them just asks for them as a parameter.

**Alembic migrations, and why you never hand-edit the schema.** SQLAlchemy models describe what the database *should* look like in Python; Alembic is the tool that gets an actual live database to match that description, one small, versioned step at a time. Each migration is a Python file with an `upgrade()` and a `downgrade()` function, and Alembic keeps a table in the database recording which migrations have already been applied. If you connected to Postgres and manually ran `ALTER TABLE`, three problems follow immediately: nobody else on the team, and no other environment (staging, a teammate's laptop, production), would automatically get that change; there would be no record of *why* the change happened or in what order relative to other changes; and Alembic's own bookkeeping table would now disagree with reality, so the next real migration could easily fail or, worse, silently do the wrong thing. Treating the migration history as the single source of truth for schema changes, and never touching the schema any other way, is what keeps every copy of the database in the same shape.

**Celery workers and tasks, and why long work does not run in the request handler.** An HTTP request has an implicit contract: the client is waiting, and a reverse proxy, a load balancer, or the browser itself will eventually give up if the server does not respond within some number of seconds. Extracting 150 requirements from a tender by calling an LLM once per chunk, or running OCR across 40 scanned pages, can easily take minutes. If that work happened inside the request handler, either the request would time out with the work still running (and the client would have no idea whether it succeeded), or you would need one web server thread tied up per slow upload, which does not scale. Celery solves this by splitting "describe the work" from "do the work": your FastAPI route creates a database row describing the job and calls `some_task.delay(...)`, which serializes the task name and its arguments and drops them onto a queue (in this codebase, Redis). A separate long-running process, the Celery worker, watches that queue, picks up jobs, and executes the corresponding Python function, completely decoupled from any particular HTTP request. The web process and the worker process can even run on different machines. The request handler that queued the work returns to the client almost instantly, and the client finds out how the job is going by some other channel, here a WebSocket.

**What Redis is doing here.** Redis is an in-memory data store that this backend uses for three distinct jobs, and it is worth keeping them mentally separate even though it is the same running Redis instance. First, it is the Celery broker: the queue that task messages sit in between being created by a web request and being picked up by a worker. Second, it is a small key-value cache for progress state: whenever a Celery task advances a stage, it writes the latest progress payload to a Redis key with a TTL, and also publishes that same payload on a Redis Pub/Sub channel, so a WebSocket that connects late can read the key for "what's the current state" and then subscribe to the channel for "what happens next." Third, it holds short-lived, single-use tokens: WebSocket connection tickets (`app/services/ws_tickets.py`) and password-reset redemption markers (`app/services/password_reset_tokens.py`), both taking advantage of Redis's atomic operations (`GETDEL`, `SET ... NX`) and automatic expiry (`EX`) to implement "usable exactly once, and only briefly" without any extra bookkeeping table.

**WebSockets, and why progress uses one instead of polling.** An ordinary HTTP request is one question and one answer; the connection then closes. A WebSocket is a single connection that both sides keep open and can send messages over in either direction, at any time, for as long as it stays connected. For a tender that takes two minutes to process, you could poll (have the browser ask "are you done yet?" every second) but that means either a noticeable delay between something actually changing on the server and the browser learning about it, or a lot of wasted requests that come back with "still working." A WebSocket lets the server push a message the instant something changes, and the browser just reacts to it, using one connection instead of a hundred short-lived ones. The cost is that a WebSocket handshake cannot carry a normal `Authorization` header the way `fetch()` can, which is why this codebase authenticates its two progress sockets with a short-lived ticket passed as a query parameter instead (see `ws_tickets.py` in the file walkthrough below).

**JWT access and refresh tokens.** A JSON Web Token is a small, signed, self-contained piece of data: a payload (here, the user's id, role, token type, issued time and expiry) plus a cryptographic signature that only the server, holding a secret key, could have produced. When a client presents a JWT, the server does not need to look anything up in a database to trust its contents; it just re-verifies the signature and checks the expiry. This backend issues two tokens on login: a short-lived access token (24 hours here, controlled by `ACCESS_TOKEN_EXPIRE_MINUTES`) that the client sends on every request, and a longer-lived refresh token (7 days) that the client stores and only uses to obtain a new access token once the old one expires, via `POST /api/auth/refresh`. Splitting the two means the token used on every single request is short-lived (so if it leaks, the exposure window is small) while the user does not have to log in with a password every day. A third, distinct token type, the password-reset token, is deliberately much shorter-lived (30 minutes) and, because it travels through email rather than staying in the browser, is additionally tracked in Redis so it can only ever be redeemed once, which a bare JWT cannot enforce on its own (see `app/core/security.py` and `app/services/password_reset_tokens.py` below).

**RAG and vector embeddings, and what pgvector adds to Postgres.** An embedding is a way of turning a piece of text into a fixed-length list of numbers (a vector) such that texts with similar meaning end up as vectors that are numerically close together, typically measured with cosine similarity. This lets you do "search by meaning" instead of "search by exact keyword": you embed a search query the same way you embedded your documents, then ask the database for the stored vectors closest to the query vector. pgvector is a Postgres extension that adds a native vector column type and fast nearest-neighbor operators (`<=>` for cosine distance, used throughout `app/services/library/search.py`) directly inside Postgres, so you do not need a separate specialized vector database; your embeddings live in the same tables, the same transactions, and the same backups as everything else. RAG, retrieval-augmented generation, is the pattern of using that search step as the first half of answering a question with an LLM: retrieve the most relevant passages first, then hand only those passages to the model and instruct it to answer using only what it was given, rather than letting it answer from its own general training. This backend's `services/library/rag.py` is a compact, well-commented example of exactly that pattern, including citation tracking and an explicit refusal path when nothing relevant was found.

## 3. File-by-file walkthrough

The codebase is organized as one merged backend that grew out of two earlier prototypes: a "flat" prototype that had no real authentication or database, and a fuller tender-analysis system. Wherever you see a file whose entire content is a docstring plus a `raise ImportError(...)`, that is a **tombstone**: a leftover file from the merge that has been deliberately emptied so that importing it fails loudly and immediately, rather than silently running old, incompatible code. The project's own convention (explained fully under `app/config.py` below, and worth internalizing as a pattern in its own right) is: when two modules of the same or similar name exist after a merge and only one is wired into the running app, do not just delete the loser and hope nobody references it by memory; replace its body with a `raise ImportError(...)` that names the real module. A stray `import app.config` then fails at the exact line that would otherwise have silently produced a half-configured app, instead of failing mysteriously three modules later, or not failing at all and just being wrong.

### 3.1 `app/` root

**`app/__init__.py`** is empty. It exists only so Python treats `app/` as a package, allowing `from app.core.config import get_settings` style imports.

**`app/config.py`** is a tombstone superseded by `app/core/config.py`. It belonged to an earlier flat-layout prototype that had its own `Settings` class exposing a single `STORAGE_DIR`. The live configuration module splits storage into four separate roots and adds JWT, Celery and CORS settings the prototype never needed because its authentication was a hardcoded stub. The docstring is explicit that nothing in the running tree imports this file (verified by grep before it was emptied) and that it is safe to delete outright; it is kept only because whatever tooling performed the merge could not delete files. This file is the best place in the repo to read the tombstone pattern's own reasoning in the author's words, and it is worth reading once even though you should never import it.

**`app/db.py`** is a tombstone superseded by `app/core/database.py`. It defined its own SQLAlchemy engine, sessionmaker and declarative `Base` from the flat prototype. The docstring calls out the specific failure this tombstone exists to prevent: two separate `Base` classes in one process. If a second `Base` existed and some model accidentally registered against it, Alembic's autogenerate (which walks `Base.metadata`) would not see those tables and would propose dropping them, and a `get_db` imported from this file would hand out sessions bound to an entirely different connection pool than the rest of the app uses. This is a genuinely dangerous class of bug to have lying around importable, which is exactly why it raises instead of just sitting unused.

**`app/main.py`** is the live FastAPI entrypoint, the only one that should ever be run with `uvicorn app.main:app`. It builds the `FastAPI()` app, adds `CORSMiddleware` (needed because the frontend runs on a different origin, `localhost:5173`, than the API), conditionally mounts a static `/demo` directory if one exists on disk (resolved relative to the file itself rather than the process's working directory, so `uvicorn` still boots correctly no matter which folder you launch it from), and includes six routers: `auth`, `tenders`, `ws`, `library`, `library_ws`, and `health`. It also defines a plain `GET /health` endpoint that does a real `SELECT 1` against Postgres through the shared `engine`, so a liveness probe actually proves the database is reachable rather than just proving the Python process is alive. Every other route file plugs into the app only through this module; if you add a new router, this is where you register it.

**`app/models.py`** is a tombstone, but a different flavor from `config.py` and `db.py`: it is *unreachable by construction*, not merely unimported. Because `app/models/` exists as a package (a directory with an `__init__.py`), Python's import system always prefers the package over a same-named `.py` file sitting beside it, so `import app.models` can only ever resolve to `app/models/__init__.py`; this flat file is never executed at all, and its `raise` is documentation rather than an active guard. It still carries a full explanatory docstring pointing at the real package, which matters because a reader who opens the file in an editor has no way to tell from the filename alone that it never runs.

**`app/schemas.py`** is the same situation as `app/models.py`: shadowed and unreachable because `app/schemas/` is a package. Its docstring points to the three live schema modules (`auth`, `library`, `tender`).

### 3.2 `app/api/`

**`app/api/__init__.py`** and **`app/api/routes/__init__.py`** are both short docstring-only files that describe the layout rather than doing anything: HTTP concerns live under `app/api/`, `deps.py` holds the shared auth dependencies, and each router module under `app/api/routes/` owns its own `APIRouter(prefix=...)` so adding an endpoint never means touching `app/main.py`'s setup beyond one `include_router` call.

**`app/api/deps.py`** defines the two dependency functions almost every protected route in the app uses: `get_current_user` and `require_role(*roles)`. `get_current_user` takes the credentials extracted by FastAPI's `HTTPBearer` security scheme (which itself already returns 403 if the header is missing) and the DB session, decodes the JWT, checks that its `type` claim is specifically `access` (rejecting a caller who passes a refresh token where an access token belongs), looks up the user by the token's `sub` claim, and 401s if the token is invalid, expired, wrongly-typed, or the user no longer exists or has been deactivated. `require_role(*allowed_roles)` is a *dependency factory*, a function that returns a dependency function, which is the idiomatic FastAPI way to parameterize a check: `Depends(require_role(UserRole.ADMIN))` builds a fresh closure around the specific roles that route needs, layered on top of `get_current_user`, and 403s if the user's role is not in that set. The module's docstring makes an important conceptual point worth remembering as you move to other frameworks: FastAPI has no separate "middleware" concept for per-route authorization the way some other frameworks do; the idiomatic equivalent is exactly this, a dependency every protected route opts into.

**`app/api/library.py`** and **`app/api/ws.py`** are both tombstones from the flat prototype, superseded by `app/api/routes/library.py` and (jointly) `app/api/routes/library_ws.py` plus `app/api/routes/ws.py`. Both docstrings flag the same serious risk their existence as a tombstone protects against: the prototype versions were built against a no-op `DEV_PRINCIPAL` stub instead of real authentication, so if either were ever accidentally registered on the live app (even by accident, even as a second, redundant registration), it would expose an entire unauthenticated copy of the Evidence Library API, or an unauthenticated WebSocket that anyone could connect to just by guessing an id. `ws.py`'s tombstone also explains why the live backend has *two* separate progress WebSocket routers rather than one shared one: the tender pipeline publishes progress on a Redis channel keyed by tender id with a 24-hour-TTL snapshot key, while the library indexing pipeline publishes on a differently-shaped channel keyed by index-job id and replays from the persisted `index_jobs` database row instead of a Redis snapshot. The two progress systems genuinely differ in payload shape and replay semantics, so merging them back into one router would be a real regression, not just tidying.

**`app/api/routes/auth.py`** implements registration, login, refresh, "who am I," and the forgot/reset password flow. `register` hashes the password with bcrypt (via `app/core/security.py`) and deliberately has no `role` field on the request body at all, so nobody can self-elevate to admin over the API; the code comment is explicit that promoting a user to admin is meant to happen out of band. `login` implements the account lockout requirement: it checks `locked_until` before even checking the password, and on a wrong password increments `failed_login_attempts`, locking the account for `FAILED_LOGIN_LOCKOUT_MINUTES` once the count reaches `FAILED_LOGIN_LOCKOUT_THRESHOLD` (five, by default). It returns the exact same "Incorrect email or password" error whether the email does not exist or the password is wrong, which stops an attacker from using the login endpoint to discover which emails are registered. `refresh` decodes the refresh token, checks its type is specifically `refresh`, and mints a fresh access/refresh pair; note it does not invalidate the old refresh token, so this is a straightforward stateless refresh rather than a rotating one. `forgot_password` and `reset_password` implement a full password-reset loop: a signed, 30-minute `password_reset` JWT is emailed as a link, and redeeming it goes through `app/services/password_reset_tokens.py`'s Redis-backed single-use check before the password is actually changed, specifically so a link sitting unread in an inbox for a week cannot be used twice even though the JWT itself would otherwise still verify. A successful reset also clears any active lockout, on the reasoning that a forgotten password is often the very reason an account got locked out in the first place.

**`app/api/routes/health.py`** exposes one endpoint, `GET /api/health/llm`, that round-trips a trivial prompt through the exact same Anthropic client configuration (`AsyncOpenAI` instance, base URL, model) that `services/extraction.py` uses for real tender extraction, and reports what happened. Its docstring explains the actual problem it solves: without it, an operator whose tender extraction fails has to guess whether the cause was a bad API key, a retired model name, a network block from the worker, or a spent quota, by re-running a full tender and reading worker logs. This endpoint answers that in a couple of seconds. It always returns HTTP 200, distinguishing "the probe ran and here is what it found" (`ok: true`/`false` in the body) from "the probe itself crashed" (which would be a 5xx); the design intent is that a caller checks one field in one response shape rather than two different response shapes depending on outcome.

**`app/api/routes/library.py`** is the live Evidence Library REST router. It splits upload and training into two separate calls on purpose: `POST /{category}/upload` only validates the file, computes a SHA-256 hash, checks for an exact or near duplicate against already-indexed documents (via `services/library/search.check_duplicate`), and stores the bytes plus a `Document` row in `QUEUED` state; nothing is parsed or embedded yet, because the duplicate check has to happen before any CPU is spent on a file that might just get rejected. `POST /train` is what actually enqueues Celery indexing jobs, either for a specific list of document ids or, if none are given, for everything still `QUEUED`; documents already `INDEXED` are skipped unless `force=true` is passed, which is what makes incremental training genuinely incremental rather than reprocessing the whole library every time one new asset is added. The rest of the router is largely read/list/detail endpoints, a `/search` endpoint that is the seam Stage 3 tender matching calls into directly, an `/ask` endpoint that calls into `services/library/rag.answer`, and two file-serving endpoints (`/documents/{id}/file` for the original upload, `/documents/{id}/images/{name}` for extracted images) that both defer to `Path.resolve()` plus `is_relative_to(...)` checks against the storage root before serving anything, specifically to stop a crafted id or filename from being used to read arbitrary files off the server's disk. `_get_document` is written with an explicit comment that there is no per-user ownership check: the Evidence Library is a shared resource for the whole sales team by design, and `uploaded_by` exists for attribution, not access control.

**`app/api/routes/library_ws.py`** is the live library indexing progress WebSocket, at `/ws/library/{job_id}`. On connect it authenticates via a single-use ticket (see `services/ws_tickets.py`, described below), immediately replays the current `IndexJob` row from Postgres so a client that reloads mid-run does not sit on an empty progress bar, and then subscribes to that job's Redis Pub/Sub channel and forwards every frame it receives until a terminal stage (`complete` or `failed`) arrives. It periodically sends a `{"type": "ping", ...}` frame when nothing new has arrived within its poll timeout, both to stop an idle proxy from closing the socket during a long parse and to reliably notice a client that has gone away. The whole handler is wrapped in one `try` so that a client closing the tab the instant it connects (which can make even the very first `send_json` raise `WebSocketDisconnect`) is treated as a normal end of stream rather than an unhandled exception.

**`app/api/routes/tenders.py`** is the largest route module and covers the tender upload plus every read and review action that happens after the pipeline runs. `upload_tender` is deliberately thin: it validates the file, creates a `Tender` row in `UPLOADED` state, saves the bytes to disk, publishes an initial progress message, and calls `enqueue_pipeline(...)`, returning in milliseconds; everything from parsing onward runs in the Celery task described under `app/tasks/tender_pipeline.py`. `_get_tender` carries the same explicit "no owner check, this is a shared workspace" comment as the library router's `_get_document`. `review_match` implements the accept/reject/reassign action a human takes on one suggested piece of evidence, and re-fetches the row with its relationships eagerly loaded before serializing the response, since a plain `db.commit()` does not automatically refresh related objects the response schema needs. `cancel_tender` and `reprocess_tender` are the two routes that manipulate `run_generation`, the counter that guards against a stale worker overwriting a newer run's state; both routes bump the counter and the reasoning for exactly why is explained in depth under `app/tasks/tender_pipeline.py` below, since that is where the counter is actually enforced. `finalize_tender` recomputes the report and reassembles the output folder against whatever match decisions a human has made so far, then publishes a `FINALIZED` status, which is a terminal state for the progress socket. `report_tender_issue` is worth reading closely: its docstring states plainly that the actual failure email is composed and sent from the *user's own mailbox* via a frontend-opened `mailto:` link, and this endpoint only records that the hand-off happened (`support_requested_at`), so it does not itself send anything; that matters when you get to `services/support_email.py` below, because that service module implements SMTP sending for exactly this scenario but, as things stand in this codebase, is never actually called from any route. That is worth flagging as a concrete lesson: a fully-built, well-documented service module is not proof that it is wired into a live code path, and it is worth grepping for a function's call sites before assuming a docstring describes current behavior.

**`app/api/routes/ws.py`** is the live tender-progress WebSocket, `/ws/tenders/{tender_id}/progress`. It authenticates with a ticket exactly like the library socket does, then, on connect, calls `get_latest_progress(tender_id)` to read the Redis snapshot key and send it immediately (so a reconnecting client sees current state before any new event fires), and if that snapshot is already terminal (`finalized` or `failed`), closes the socket right there rather than waiting on a Pub/Sub message that will never come. Otherwise it subscribes to the tender's Redis channel and loops, using a short `get_message(timeout=1.0)` poll interleaved with a very short `receive_text(timeout=0.01)` check, so it notices a client disconnect promptly without blocking forever on either side. Unlike the library socket, this one talks to Redis using `redis.asyncio` directly rather than going through a shared helper module, which is a small inconsistency worth noticing rather than imitating; it works, but it means the connection-management code is duplicated rather than shared between the two socket routers.

### 3.3 `app/celery_app.py`

This module constructs the single `Celery` application instance used by the whole backend, named `"evidence_library"` (a naming leftover from when only the library pipeline used Celery, now shared by the tender pipeline too), pointed at Redis as both broker and result backend, and explicitly lists its two task modules (`app.tasks.library_indexing` and `app.tasks.tender_pipeline`) via `include=[...]` rather than relying on autodiscovery. Its configuration choices are worth reading closely because each one encodes a real operational decision: `worker_prefetch_multiplier=1` stops one worker process from grabbing several queued jobs at once while a sibling worker sits idle, which matters because indexing and extraction are CPU- and I/O-heavy rather than trivially fast; `task_acks_late=True` means a job is only marked done after it actually finishes, so a worker that crashes mid-job does not silently lose that job; and `task_soft_time_limit`/`task_time_limit` give a long-running task a chance to record its own failure state before Celery kills it outright, rather than just vanishing. The final line, `celery_app.set_default()`, has a specific and slightly subtle reason documented in the file: Celery's `current_app` is thread-local, populated only on the thread that imported this module, and FastAPI runs synchronous route handlers on a worker thread pool, so without this call, a sync route trying to enqueue a task from a different thread could resolve `current_app` to a lazily-created default Celery app pointed at the wrong broker entirely (`amqp://localhost:5672`), producing a confusing "connection refused" even though the real Redis URL is configured correctly.

### 3.4 `app/core/`

**`app/core/__init__.py`** is a one-line docstring explaining that this package holds cross-cutting infrastructure with no dependency on `app/api` or `app/services`, so it can be imported from anywhere without creating an import cycle. That is a useful discipline to notice: `core/` is meant to sit at the bottom of the dependency graph.

**`app/core/config.py`** is the live `Settings` class, read once via `@lru_cache get_settings()` and used everywhere else in the app instead of scattering `os.getenv(...)` calls throughout the codebase. Reading it top to bottom is close to reading the whole backend's feature list: database and Redis URLs, JWT secret and lockout thresholds, four separate storage roots (root, tender, library, output), the embedding provider/model/dimension (with an explicit comment that the dimension is not a free parameter, since two `vector(768)` columns are already committed to it and changing it means a migration), one shared Anthropic API key powering three different features (tender extraction, library auto-tagging, and the grounded Ask), two different model names for cost tiering (explained fully under `services/extraction.py` below), and SMTP settings shared by two unrelated email features. The docstring on `ANTHROPIC_USER_AGENT` is worth reading on its own: an earlier version of this configuration deliberately overrode the outbound `User-Agent` header to impersonate Anthropic's own first-party CLI, in order to get past a third-party reseller's allowlist; this version removed that override because it now talks to Anthropic directly, and the comment states outright that impersonating another client was never something to keep, reseller workaround or not. That is a small but genuine lesson in how prototype code decisions do not always survive review, and why leaving a comment explaining *why* something was removed is as valuable as the removal itself.

**`app/core/database.py`** builds the single SQLAlchemy `engine` and `SessionLocal` sessionmaker, and defines `get_db()`, the FastAPI dependency essentially every database-backed route uses. `get_db` is a generator function: it creates a session, `yield`s it (which is what lets FastAPI hand that same session to your route function as `db: Session = Depends(get_db)`), and the code after the `yield`, inside a `finally`, runs once the request is finished, closing the session unconditionally whether the route succeeded or raised. `pool_pre_ping=True` is a small but practically important setting: it makes the connection pool test a connection before handing it out, which avoids a class of "server closed the connection unexpectedly" errors that show up after a database connection has sat idle for a while (a common annoyance on a laptop that just woke from sleep, or after a database restart).

**`app/core/security.py`** holds password hashing and JWT creation/decoding, kept in one file specifically because it has no dependency on the database or on FastAPI request objects, making it trivially unit-testable in isolation and reusable from anywhere. `hash_password`/`verify_password` wrap `passlib`'s bcrypt context. `_create_token` is the shared internal helper behind `create_access_token`, `create_refresh_token`, and `create_password_reset_token`, each of which just picks a different `TokenType` and expiry. `decode_token` deliberately only proves the signature and expiry are valid; it does not check which *kind* of token was presented, that check is left to each caller (`get_current_user` checks for `type == "access"`, the refresh route checks for `type == "refresh"`), which matters because otherwise a leaked long-lived refresh token could be used directly as an access token. `create_password_reset_token` additionally mints a random `jti` (JWT ID) claim precisely so the reset route can mark that one specific token as redeemed after use, something a bare JWT's signature alone can never do since anyone holding an unexpired copy of a JWT can normally present it as many times as they like.

**`app/core/ws_manager.py`** defines `TenderProgressConnectionManager`, an in-process registry mapping a tender id to the set of currently-open WebSocket connections watching it, with a `broadcast()` method that pushes a JSON payload to every socket watching one tender and quietly drops any socket that has gone stale. Its own docstring is candid that this design only works because it assumes a single Python process holding both the WebSocket connections and the code that produces updates, and explicitly warns that once the real pipeline runs in a separate Celery worker process, `broadcast()` would need to go through Redis Pub/Sub instead, since two separate OS processes cannot share one Python dictionary. That is exactly what happened: the live tender pipeline does run in a Celery worker, and the live progress route (`app/api/routes/ws.py`) was rewritten to talk to Redis directly rather than to this manager. A grep across the whole codebase confirms `ws_manager` is not imported anywhere outside this file itself; the module is genuinely dead code in the running app, but unlike the files under `app/config.py` and its siblings, it was never converted into a tombstone that raises on import, it is simply unreferenced. That is a useful thing to notice as a student: dead code does not always announce itself, and "grep for who imports this" is a habit worth having whenever you are not sure whether a module you are reading actually runs.

### 3.5 `app/models/`

**`app/models/__init__.py`** imports every model class so that importing the package as a whole registers all of them on `Base.metadata`. Its docstring states the real reason this matters: Alembic's `env.py` imports this module specifically so that `alembic revision --autogenerate` can see every table when comparing the current models against the live database schema. If a model file existed but was never imported anywhere, Alembic's autogenerate would simply not see it and could propose dropping tables that model actually needs, purely because nothing pulled that file into memory before the comparison ran. This is the concrete, practical reason "import everything in one place" is a pattern worth following rather than an arbitrary style choice.

**`app/models/base.py`** defines the shared `Base` declarative class every model inherits from, plus two mixins, `UUIDPKMixin` (a client-side-generated UUID primary key, chosen so the app does not depend on a Postgres extension like `pgcrypto` being enabled for server-side UUID generation) and `TimestampMixin` (timezone-aware `created_at`/`updated_at`, both defaulted in application code rather than by a database-side trigger, so the same value is guaranteed no matter which code path writes the row). Almost every model in the package inherits both mixins, which is why you will not see `created_at` or `id` redeclared table by table.

**`app/models/enums.py`** centralizes every enum shared across models, and each one is written to Postgres as a native `ENUM` type via SQLAlchemy's `Enum(..., name=...)`, rather than a plain string column, so the database itself rejects a value outside the allowed set at the storage layer, not just in application code. Reading this file top to bottom is a fast way to understand the shape of the whole domain: `UserRole` (only `admin`/`user`, with a comment noting the original spec's third role was folded into `user`), `DocumentCategory` and `DocumentFileType` for the library, `DocumentTrainingStatus` and the closely related but deliberately distinct `JobStage` (the former is "what state is this document in right now," the latter is "how far did this specific training run get," and re-training an already-indexed document starts a fresh job at `queued` while the document itself correctly stays `indexed` until the new run finishes and replaces its chunks), the two lookup tables `JOB_STAGE_LABELS` and `JOB_STAGE_TO_DOCUMENT_STATUS` that keep the job-stage-to-document-status mapping in exactly one place so the two can never silently drift apart, `TenderStatus` (the eight pipeline stages plus the two terminal states), `EvaluationImpact`, `RequirementStatus`, and `MatchType`/`MatchReviewStatus` for the evidence-matching review workflow. The comment on `MatchType` is worth noting: it states the exact confidence thresholds (0.85 for `auto`, 0.60 to 0.84 for `suggested`) and explicitly instructs that these must be kept in sync with the equivalent constants in `app/tasks/tender_pipeline.py`, an example of a business rule that has to live in two places (an enum's documentation and a task's actual threshold constants) because the enum itself cannot enforce a numeric range.

**`app/models/user.py`** defines the `User` table: name, email (unique, indexed), a bcrypt password hash, role, an `is_active` flag, the two columns that implement account lockout (`failed_login_attempts`, `locked_until`), and `last_login_at`. Its relationships (`uploaded_documents`, `uploaded_tenders`, `audit_logs`) are declared with explicit `foreign_keys=` arguments because more than one foreign key in this schema can point at `users.id` (for example, both `uploaded_by` and `reviewed_by` on different tables), and SQLAlchemy needs to be told unambiguously which column a given relationship should join on whenever more than one plausible column exists.

**`app/models/document.py`** defines `Document`, the single table backing all three Evidence Library categories (case study, methodology, company document) rather than three separate tables, on the reasoning that the categories differ only in *how* a file is parsed, not in what metadata it needs to carry. It carries the LIB-UI-03 metadata fields (client, sector, service line, geography, keywords), a unique, indexed `file_hash` used for the exact-duplicate check, the LIB-UI-05 training status, and the Section 6 additions layered on top (`doc_type`, `auto_tagged_fields`, `page_count`, `chunk_count`, `indexed_at`). `DocumentImage` is a small child table recording where an extracted image was written on disk, by path only; images are never stored as pixel data inside a row.

**`app/models/chunk.py`** defines `Chunk`, one embedded passage of a library document, with a `UniqueConstraint` on `(document_id, chunk_index)` and an `embedding` column typed `Vector(EMBEDDING_DIM)` from the `pgvector` SQLAlchemy integration. It denormalizes `category` from the parent `Document` directly onto the chunk row specifically so a category filter can be applied to a vector search without first joining back to `documents`, which matters for query performance once the library has many chunks.

**`app/models/index_job.py`** defines `IndexJob`, one row per Train/Memorize run, existing specifically so training progress survives a page reload; it is the persisted counterpart to the live Redis Pub/Sub frames the library WebSocket streams, and its own `stage`/`progress`/`message` columns are exactly what `library_ws.py`'s snapshot replay reads on connect.

**`app/models/audit_log.py`** defines a deliberately generic `AuditLog` table (`action`, `resource_type`, `resource_id`, a free-form `details` JSON blob) so that one table can log logins, tender runs, document training and user-management actions without a separate table per action type; `user_id` is nullable because some events (a failed login attempt against an unknown email, or a system-level error) have no authenticated user to attach the entry to.

**`app/models/tender.py`** defines `Tender`, the largest single model in the app, tracking one uploaded document through all eight pipeline stages plus best-effort metadata (reference id, issuing authority, sector, location, value, deadline) filled in by a single LLM pass and correctable by the user afterward via `PATCH`. Its comment block on the failure-record columns (`failed_stage`, `error_detail`, `failed_at`) explains a real design problem worth understanding: `progress_message` alone is not enough to build an error log, because every pipeline stage overwrites it, so by the time a run has failed there is no record of *which* stage actually died or what the underlying exception was, once a retry has started overwriting the same column again. The three dedicated failure columns exist purely to survive that overwrite, and all three are explicitly cleared on a successful reprocess so the row always describes only the current attempt. The `run_generation` and `celery_task_id` columns are the mechanism behind cancel/reprocess safety and are explained in depth under `app/tasks/tender_pipeline.py`, since that is where they are actually enforced rather than merely stored.

**`app/models/requirement.py`** defines `Requirement` (one row per extracted requirement, with both a normalized column and a verbatim `_raw` column for several fields, because real tenders write compound or non-boolean values like "No/Advisory" or "Financial / Pass-Fail" that a clean enum or boolean cannot hold, and the output tracker has to reproduce the tender's own wording exactly) and `RequirementEvidenceMatch`, a separate child table rather than a single foreign key on `Requirement`, specifically because a requirement can have more than one candidate evidence document (auto-matched, several suggested candidates, or a "missing, here's the closest we found" candidate) each with its own confidence score and its own independent accept/reject/reassign review history.

**`app/models/tender_chunk.py`** defines `TenderChunk`, and its docstring is a clear worked example of why two similarly-named tables should sometimes stay separate rather than be merged: `Chunk` (library) and `TenderChunk` (tender) are both "a piece of a document with an embedding," but they have different owners, different chunk sizes and overlap, and different downstream consumers, so conflating them would make both harder to reason about even though the underlying idea is the same.

### 3.6 `app/schemas/`

**`app/schemas/__init__.py`** is a short docstring repeating the request/response versus database boundary explained in the core concepts section above.

**`app/schemas/auth.py`** defines the request and response shapes for the auth endpoints: `RegisterRequest` (with `password: str = Field(min_length=8, max_length=72)`, the 72-character maximum being bcrypt's own hard input limit, not an arbitrary choice), `LoginRequest`, `RefreshRequest`, the forgot/reset password request pair, `UserOut` (configured with `model_config = {"from_attributes": True}`, which is what lets Pydantic build this schema directly from a SQLAlchemy `User` object's attributes rather than requiring a plain dict), and `TokenResponse`, which nests a `UserOut` inside itself so a successful login returns both tokens and the user's own profile in one response.

**`app/schemas/library.py`** is the largest schema module and defines everything the library router returns: `MetadataInput` for uploader-supplied fields, `ChunkOut`/`DocumentOut`/`DocumentDetailOut` for read responses, `UploadResponse` plus the `DuplicateMatch`/`DuplicateCheckResult` pair for LIB-UI-06's duplicate warning, `TrainRequest`/`TrainResponse`/`JobOut` for the training flow, `WsTicketOut` for the library progress ticket, `ProgressEvent` describing exactly what crosses the WebSocket, `SearchHit`/`SearchResponse` for plain retrieval, and `AskRequest`/`AnswerOut` for the grounded-answer endpoint. A small but genuinely useful pattern shows up here repeatedly: several fields use `field_validator(..., mode="before")` helpers like `_blank_if_none` and `_empty_list_if_none` to normalize a `NULL` database value into an empty string or empty list before validation runs, specifically because the underlying columns are nullable (rows can have been written by a different code path than the one that always writes `""`), and the API contract promises clients one consistent shape (never `null` where a string or list is expected) regardless of which code path produced the row.

**`app/schemas/tender.py`** defines the tender-side schemas, and its module docstring explains a small, easy-to-miss decision worth remembering for your own projects: money and marks columns are `Numeric` in the database (for exact decimal precision) but are typed as plain `float` in these Pydantic schemas, because Pydantic serializes a `Decimal` to a JSON *string* in its default JSON mode, which would force the frontend to parse every currency and marks value back into a number itself; keeping the wire format as a JSON number and letting the database column remain the actual source of truth for precision is a deliberate tradeoff, not an oversight. `TenderReportOut`'s field comments are worth reading closely for how they define "coverage": a requirement only counts toward `requirements_with_evidence`/`requirements_without_evidence` if `evidence_required` is true in the first place, because a narrative clause the tender never asked the bidder to prove would otherwise get mislabeled as "missing evidence" purely because nobody ever tried to match it.

### 3.7 `app/services/` (root)

This is the directory where the "old prototype versus live module" split is most extensive, and it repays reading carefully because it demonstrates the tombstone pattern at scale rather than in one or two isolated files.

**`app/services/__init__.py`** states the organizing principle directly: two families of service modules live under `app/services/`, the tender pipeline (chunking, PDF extraction, extraction, pipeline stage labels, progress, tender storage, all directly under `app/services/`) and the Evidence Library (entirely under the `app/services/library/` subpackage), and they are not merged because `chunking` and `progress` exist under both names with genuinely different behavior, which is exactly why the library's copies are namespaced under `library/` instead of living flat beside the tender versions.

**`app/services/chunking.py`** is live, not a tombstone, and it is easy to mistake for one given how many of its neighbors are tombstones. It implements section-aware chunking for tender documents: detecting section boundaries by regex (SPN, Instructions to Proposers, PDS, Evaluation Criteria, Section VII, Annexes, falling back to a generic "General/Front Matter" label), grouping consecutive pages by detected section, then splitting each section into roughly 2000-token windows with roughly 200 tokens of sliding overlap between consecutive chunks. What makes this module worth reading closely is the comparison the docstring draws against the prototype it replaced: the prototype tracked only a page *range for the whole section*, then blindly token-split the concatenated text, so any chunk after the first one in a multi-chunk section had no real page attribution at all; this version tokenizes per page and keeps a running token-offset-to-page map (using `bisect` for an efficient lookup) so every individual chunk gets a true `page_start`/`page_end`. It also had genuinely no overlap at all in the prototype despite the spec calling for it, meaning a requirement that happened to fall across a chunk boundary could be silently lost; this version actually slides the window. `guard_against_whole_document_ingestion` is a small but important safety check: it raises if any chunk exceeds the token budget or if chunking produced zero chunks for a non-empty tender, both of which would otherwise let something oversized or silently empty flow into the expensive LLM extraction stage undetected.

**`app/services/embeddings.py`**, **`app/services/metadata.py`**, **`app/services/rag.py`**, **`app/services/search.py`**, **`app/services/storage.py`**, and **`app/services/llm.py`** are all tombstones, each superseded by its like-named counterpart under `app/services/library/`. Their docstrings share a consistent shape worth noticing as a pattern: each one names the exact live replacement, explains the concrete technical reason the old copy cannot simply be revived (it was built against the tombstoned flat `app.config`/`app.db`/`app.models`, or against database columns a later migration added that the old model definition does not have, or, in `llm.py`'s case, against a `User-Agent` impersonation setting that no longer exists on the live `Settings` class at all), and states plainly that the file is safe to delete and is only kept because the merge tooling could not delete files. `storage.py`'s docstring is worth a specific mention: it explains that the flat prototype resolved everything under one `STORAGE_DIR` setting, and because the live `Settings` class is configured with `extra="ignore"`, a stray `STORAGE_DIR` entry left in a `.env` file would not raise an error, it would simply be silently swallowed and paths would quietly fall back to their defaults; that silent-failure risk is exactly why this module was tombstoned outright rather than just left unused.

**`app/services/parsers/` (whole subpackage)**, `__init__.py`, `base.py`, `case_study.py`, `company.py`, `extract.py`, `methodology.py`, `registry.py`, is a tombstone package superseded wholesale by `app/services/library/parsers/`. The package `__init__.py` raises on its own, which is what makes every submodule inside it unreachable even before Python gets to executing them individually (each submodule still carries its own explanatory raise as "a second line of defence for anyone who copies the file elsewhere," in the codebase's own words, which is a reasonable defensive habit: a tombstone that only guards at the package level can be defeated by copying one file out of the package). The package docstring explains why the live parsers live under `library/` specifically rather than being merged flat: parsing is one of the places the tender side and the library side genuinely differ in kind, not just in tuning, since the library parsers are section-oriented and produce library `Chunk` rows while the tender side parses page-oriented PDFs through `pdf_extraction.py` and `chunking.py` into a different dataclass entirely.

**`app/services/password_reset_tokens.py`** is live and implements single-use redemption tracking for the password-reset JWT described earlier. Its `redeem(jti, ttl_seconds)` function is a small, worked example of a genuinely important concurrency pattern: it uses `SET ... NX` (set-if-not-exists) against Redis, which performs the "is this already used, and if not, mark it used" check as one atomic server-side operation, returning `True` only the first time a given `jti` is redeemed and `False` on every call after, including a second request racing the first by microseconds. A naive "read the key, check if it exists, then write it" implementation would have a race window between the read and the write where two near-simultaneous requests could both see "not yet redeemed" and both succeed; `SET NX` closes that window entirely by doing both steps as one indivisible operation.

**`app/services/pdf_extraction.py`** is live and extracts per-page text plus tables from a tender PDF using PyMuPDF, falling back to Tesseract OCR on any page whose extracted text is suspiciously short (under `OCR_FALLBACK_CHAR_THRESHOLD`, on the reasoning that a page with real text rendered as an image is the signature of a scan). It is built on the same core approach as an earlier prototype, but the docstring flags one specific, easy-to-miss bug the prototype had: it hardcoded a Windows path to the Tesseract binary at *import time*, which is global to the `pytesseract` module, meaning it silently redirected the Evidence Library's own, separate OCR path as an unrelated side effect of merely importing this module, and it broke entirely inside Docker, where the binary lives somewhere else. This version makes the Tesseract path opt-in via an environment variable, verified to actually exist on disk before being applied, and falls back to resolving `tesseract` from `PATH` otherwise, which is a small but real lesson about avoiding module-level side effects that reach outside the module doing them.

**`app/services/tender_storage.py`** validates (must be a `.pdf`, under 100MB, non-empty) and saves an uploaded tender to disk under `TENDER_STORAGE_DIR/{tender_id}/{filename}`, keyed by the tender's own UUID so two uploads that happen to share a filename never collide. Its docstring explains why it is named `tender_storage.py` rather than the more generic `storage.py`: keeping tender uploads and library uploads in separate modules, each targeting its own storage root, avoids exactly the kind of accidental grab-bag module two unrelated features both end up depending on, which is the same discipline `app/services/storage.py`'s tombstone explains from the other direction.

**`app/services/extraction.py`** is the LLM-based requirement extraction engine and one of the most heavily-commented files in the repo; it is worth reading in full once you understand the rest of the pipeline. `run_extraction` fans out one LLM call per `TenderChunk`, bounded by an `asyncio.Semaphore(EXTRACTION_CONCURRENCY)` so a large tender's 150-plus chunks run several at a time rather than either one at a time (slow) or all at once (likely to hit a provider rate limit), consumed via `asyncio.as_completed` specifically so the progress bar advances as each chunk finishes rather than jumping all at once at the end. Every three completed chunks (and always on the last one) it re-reads the `Tender` row from the database and, if a user has pressed Stop in the meantime (which sets the row's status to `FAILED` from a completely different request), cancels every still-running task and raises `TenderCancelled`; this is the cooperative half of the cancellation mechanism, checked from inside a loop that is otherwise just waiting on network calls it cannot interrupt any other way. `_hash_requirement` deduplicates extracted requirements by a hash of their clause reference plus description, since chunk overlap means the same requirement can genuinely be extracted twice from two overlapping chunks. The failure logic at the end of `run_extraction` is deliberately strict and ordered: if more than 30% of chunks failed after three retries each, or if zero requirements were extracted at all, the run is raised as a hard `ExtractionFailed` rather than allowed to continue to matching and reporting with a silently incomplete requirement set, because, in the module's own words, a tender extracted with 40 of 400 requirements and presented as a finished result with nothing anywhere saying so is a worse outcome than a run that fails loudly and tells the operator exactly what to check. `EXTRACTION_MODEL` is read from `ANTHROPIC_EXTRACTION_MODEL` rather than `ANTHROPIC_MODEL`, the same cost-tiering decision explained under `services/library/llm.py` below: this is high-volume, mechanical, "copy the text verbatim into these fields" work run over a hundred times per tender, which a cheap fast model does as reliably as an expensive one.

**`app/services/pipeline_stages.py`** is live and defines the ordered list of the eight tender pipeline stages plus a human-readable label for each, so the frontend does not have to turn `ASSEMBLING_FOLDER` into "Assembling Output Folder" itself. Its own docstring flags a real, deliberately-unfixed inconsistency: `app/services/progress.py` carries a second, near-identical `PIPELINE_STAGES`/`STAGE_LABELS` pair with slightly different label text ("Parsing" versus "Parsing Document," for instance), and `progress.py`'s copy is the one that actually reaches the client, since `publish_progress()` builds its payload from its own dictionary rather than this module's. This module's labels are only used by code that calls `stage_label()` directly. The docstring explicitly calls this duplication out rather than silently fixing it, on the reasoning that consolidating the two would change strings the frontend may already depend on, so it belongs in a deliberate, coordinated change rather than a quiet cleanup. That is a good habit to notice: not every piece of duplication found while reading code should be "fixed" reflexively, especially when the fix would change an external contract.

**`app/services/progress.py`** is the live Redis-backed progress publisher for the tender pipeline, described in the core concepts section above: for each tender it maintains a String key holding the latest progress payload as JSON (read on connect or reconnect, for TRK-04 resume behavior) and a Pub/Sub channel of the same logical name that is published to on every update (read live by an open WebSocket). `publish_progress` computes a percentage from the tender's position in `PIPELINE_STAGES` when no explicit percent is given, and the module has no FastAPI import at all, which is what lets the exact same function be called equally validly from an ordinary request handler or, as things stand today, from inside a Celery worker process, without either caller needing to know anything about how a WebSocket eventually delivers that update to a browser.

**`app/services/account_email.py`** sends the password-reset email over plain SMTP (`smtplib`, STARTTLS, no third-party email service), running the actual blocking send inside `asyncio.to_thread` because `smtplib` itself has no async API and the calling endpoint is async. Its docstring draws a careful distinction against its sibling `support_email.py`: both share the same SMTP transport mechanics, but `support_email.py` is deliberately never wired to a user-supplied recipient (so it can never be turned into an open relay by anything a tender or a form contains), while this module's entire job is to email a user-supplied address, so that guarantee does not and should not apply here. The two modules duplicate a small amount of SMTP boilerplate rather than sharing a helper specifically to keep that trust boundary visible and unambiguous, rather than blurred behind a shared "internal" function used by both a safe and an unsafe caller.

**`app/services/support_email.py`** composes and sends a tender's full failure detail (stage, reason, exception, stack tail, tender id) to a single configured support address, again over plain SMTP. Its docstring explains the actual product reasoning: VR-Nexus is used by non-technical procurement staff, and a raw Python traceback on screen helps nobody who cannot read it while alarming anyone who can, so the "Contact technical support" flow exists to route that traceback to people who can act on it while leaving the user with a calm, non-technical message. As already noted under `routes/tenders.py` above, this is the one place in the codebase where a fully-implemented, carefully-documented, non-tombstoned service module is nonetheless never actually called; the frontend implements the "contact support" hand-off through a `mailto:` link opened in the user's own mail client instead, and the backend route only persists that the hand-off occurred. `send_failure_report` remains here, correctly written and ready to use, but currently orphaned.

**`app/services/ws_tickets.py`** is the module the task description calls out as a model for tone and depth, and it earns that reputation. It solves one precise problem: a browser's native `WebSocket` constructor cannot set custom headers, so it cannot carry an `Authorization: Bearer <token>` the way a normal `fetch()` call can, and the naive fallback (put the real access token in the connection URL as a query parameter) means a long-lived, 24-hour bearer credential ends up sitting in browser history, in every proxy access log the connection passes through, and potentially in a `Referer` header, for as long as that token remains valid. The fix is the standard one for exactly this shape of problem: `issue_ticket(user_id, scope, resource_id)` is called from an ordinary, already-authenticated HTTP endpoint (one that *can* carry a real `Authorization` header, and whose access logs matter far less than a URL that lands in browser history), mints a random 32-byte token, and stores it in Redis with a 60-second TTL, scoped to a specific `(scope, resource_id)` pair, for example `("tender", "<tender-id>")`, so a ticket minted for one tender's progress socket cannot be pointed at a different tender's. `redeem_ticket` is where the file's most important technical detail lives: it calls Redis's `GETDEL` rather than a plain `GET` followed by a separate `DELETE`. The reasoning given is precise and worth internalizing as a pattern: a WebSocket handshake is exactly the kind of operation a client can retry, double-fire, or race against itself (a React effect re-running, a reconnect attempt racing the original connection), and a plain `GET` would let two near-simultaneous redemption attempts both see the ticket as still valid before either one deletes it. `GETDEL` reads and deletes the key as one atomic server-side step, so only the first caller to reach Redis can ever succeed, and the second sees exactly nothing, as if the ticket had never existed at all, not a race, not a rare bug, structurally impossible by construction.

### 3.8 `app/services/library/`

**`app/services/library/__init__.py`** repeats, briefly, why this exists as a subpackage rather than flat modules alongside the tender-side services: the tender side already owns modules named `chunking` and `progress`, so the library's own versions are deliberately namespaced here instead.

**`app/services/library/chunking.py`** splits a parsed section's text into roughly 800-token windows with 100 tokens of overlap, always staying within one section (never spanning, say, a case study's "Challenge" section into "Solution"), so that a chunk's section/phase/page labels stay semantically meaningful and every embedded vector represents one coherent idea rather than a boundary-straddling mash of two.

**`app/services/library/embeddings.py`** defines the `EmbeddingProvider` abstract base class and the one concrete implementation currently registered, `FastEmbedProvider`, which runs the `BAAI/bge-base-en-v1.5` model locally via the `fastembed` library (ONNX runtime, CPU-only, no external API call at all). The docstring explains a real architectural decision made partway through the project: the original implementation plan called for a hosted embedding API, but the team deliberately switched to a fully local model specifically to avoid adding a *second* API-key dependency on top of the one Anthropic key that already powers extraction, tagging and Ask, and because Anthropic itself does not serve an embeddings endpoint at all, so there was no way to keep embeddings on the same provider even if a hosted model had still been wanted. The model is loaded lazily, behind a `threading.Lock`, on first use rather than at import time, because Celery forks worker processes, and eager loading at import time would pay the (non-trivial) model-loading cost in every process including the FastAPI web process itself, which never computes an embedding on its own. `embed_documents` explicitly checks that the returned vector width matches `EMBEDDING_DIM` and raises immediately with an actionable message if it does not, rather than letting a dimension mismatch surface later as an opaque pgvector insert failure.

**`app/services/library/library_progress.py`** is the library-side twin of the tender side's `progress.py`, publishing to a differently-namespaced Redis channel (`library:progress:{job_id}` versus `tender:{id}:progress`) and never raising on a publish failure, on the explicit reasoning that a dropped progress frame should never be allowed to fail the indexing job that was trying to emit it.

**`app/services/library/llm.py`** wraps a single `openai.OpenAI` client instance pointed at Anthropic's OpenAI-compatible endpoint, used for parsing fallback and metadata auto-tagging. `complete()` returns an empty string on any failure rather than raising, and its docstring is explicit that this is deliberate: every call site in the codebase is written to tolerate a missing or failed LLM response and fall back to heuristics, so with no `ANTHROPIC_API_KEY` configured at all, the entire library pipeline still runs end to end, just without machine-assisted tagging. Its own docstring draws the same contrast as the tombstoned `services/llm.py` did, but from the winning side: the earlier version impersonated Anthropic's own CLI via a `User-Agent` override to satisfy a third-party reseller's allowlist, and this version does not, because talking to Anthropic directly means there is no reseller allowlist left to satisfy.

**`app/services/library/metadata.py`** implements LIB-IDX-06 auto-tagging with a strict, explicitly documented precedence order: whatever the uploader typed into the form always wins outright and is never touched; keyword-and-regex heuristics (sector keyword maps, service-line keyword maps, a geography gazetteer, a client-label regex) fill in whatever the user left blank; and the LLM is consulted only for fields still blank after both of those, using the cheap extraction-tier model rather than the reasoning model, on the same "mechanical field-filling" cost logic used everywhere else in the codebase. `auto_tagged_fields` records exactly which fields were machine-filled so a human reviewer can visually distinguish a typed value from a guessed one later in the UI.

**`app/services/library/rag.py`** is the generation half of the RAG pattern described in the core concepts section, and its own docstring states the design rule directly: the model is never treated as a source of facts, it only ever sees the chunks retrieval already found, is instructed to answer using only those chunks, and must produce an exact, checked-for sentinel string when the context does not answer the question. `_format_context` numbers each retrieved chunk as `[1]`, `[2]`, and so on and truncates on a whole-chunk boundary rather than mid-sentence once a hard character cap is hit, specifically because cutting a claim off mid-sentence can strand it from the qualifier that limits its meaning. `_cited_indexes` then parses the model's own answer text for exactly those bracketed numbers and marks each source hit as cited or not; a source that was retrieved but never cited is still returned to the caller rather than filtered out, because knowing what the model considered and chose not to use is itself useful information for a reviewer. `answer()`'s `grounded` flag is computed strictly: true only when the model produced at least one citation and did not decline, which means an answer that came back with prose but with nothing cited is correctly reported as ungrounded, treating an uncited answer as exactly the failure mode this whole design exists to catch, rather than quietly hiding it behind a confident-looking response.

**`app/services/library/search.py`** performs cosine-distance vector search directly against Postgres via pgvector's `<=>` operator (`Chunk.embedding.cosine_distance(vector)`), converting distance to similarity as `1 - distance`. Its docstring states a deliberate architectural choice: there is no in-memory index and no result cache anywhere in this module, every query goes straight to the live database, which is exactly what makes "a document indexed a moment ago is immediately searchable" true by construction rather than something that needs an invalidation step to keep correct. `find_near_duplicates` over-fetches (`limit * 10`) before collapsing to one best match per document, since several chunks belonging to the same document will naturally rank adjacently in a similarity search and would otherwise be counted as several separate candidate matches instead of one.

**`app/services/library/storage.py`** validates uploads by extension (deliberately not trusting the client-reported MIME type, since browsers are inconsistent about it for Office formats, and a genuinely malformed file will fail loudly during parsing anyway) and writes files to disk under a UUID-derived name rather than the client-supplied filename, which is a specific and important security detail: `save_upload`'s docstring notes plainly that because the original filename is only ever used for its file extension, a crafted filename like `../../etc/passwd` cannot be used to escape the storage directory, since nothing about the client's filename text ever becomes part of the destination path beyond its suffix.

**`app/services/library/parsers/`** is the live parser package, distinct from and superseding the tombstoned `app/services/parsers/` sibling described above. **`__init__.py`** is a one-line docstring. **`base.py`** defines the shared vocabulary every parser speaks: `Page` (one page/paragraph-block/slide of format-agnostic extracted content), `RawDoc` (the format-agnostic extraction result, with a `page_for_offset()` helper that maps a character offset in the joined full text back to the page it came from, which is what lets a downstream section parser, working purely on joined text, still attach an accurate page number to each section it finds), `Section` (a logical, chunk-ready unit of a document), `ParseResult`, and a small module-level `_REGISTRY` dict populated by each category parser calling `register(category, parser)` at import time. **`registry.py`** exists purely to trigger that registration by importing all three category parser modules, and its own docstring explains why it is a separate module rather than folded into `__init__.py`: importing `base.py` alone (for its dataclasses, say, from a test) should not have to drag in PyMuPDF, python-docx and python-pptx as a side effect, and putting the registration imports in `__init__.py` would force exactly that. **`extract.py`** is the format-specific extraction layer (PDF via PyMuPDF, DOCX via python-docx, PPTX via python-pptx, plus a bare-image path that OCRs the whole file as a single page), and its docstring is explicit about a rule enforced throughout: embedded images are written to disk and only their *paths* ever travel onward into chunk content, never raw pixel bytes or a base64 encoding, on the reasoning that a vector of pixels is not comparable to a vector of text, and storing image data inside a text column would only poison retrieval quality for no benefit. It also exposes `sample_text()`, a deliberately cheap, request-path-safe text sample (a handful of pages, no images, no OCR) used only for the upload-time duplicate check, kept separate from full extraction specifically because full extraction is far too slow to run synchronously inside an HTTP request handler.

**`app/services/library/parsers/case_study.py`** tries to resolve a case study's text into the six canonical sections (Client, Sector, Scope, Challenge, Solution, Results) by matching a broad synonym table against detected heading-shaped lines (a synonym lookup built once at import time, sorted longest-first so a more specific phrase like "project scope" is matched before a bare "scope"). If fewer than three of the six sections can be found this way, it falls back to asking the LLM (on the cheap extraction-tier model) for a section map instead, and only if that also fails does it index the document as one single undifferentiated blob, which the module's own docstring frames correctly as the last resort rather than the second choice. When the LLM path is used, the verbatim source text is kept alongside the model's own section summaries as an extra "Full Text" section, specifically so retrieval can still quote the source document directly rather than being limited to the model's paraphrase of it.

**`app/services/library/parsers/company.py`** handles certificates, registrations, tax filings and similar short single-purpose documents, and its docstring explains why it deliberately does not split these into sections at all: splitting an ISO certificate into "sections" would produce fragments like "Scope of certification" divorced from the certificate number that gives that fragment any meaning, which is worse for retrieval than simply keeping the whole short document as one unit. What this parser does instead is classify the document type using a weighted keyword-scoring table, falling back to the LLM only when the keyword score is too low to trust, and extract structured identifiers (certificate number, NTN, issue and expiry dates, issuing authority) via a set of regexes, landing all of that on the document row rather than on any individual chunk.

**`app/services/library/parsers/methodology.py`** splits a methodology document by detected phase markers ("Phase 2", "Stage III", "Step 4", numbered outline headings, or markdown headings promoted from Word/PowerPoint styles by `extract.py`), matched in that priority order, and falls back to asking the LLM for an ordered phase list only when no markers are visible at all. Its docstring explains why phase ordering specifically matters here in a way it would not for a case study: methodology documents are inherently sequential, and when the library is later asked something like "what is your approach to data migration," the phase label riding along on the retrieved chunk tells a proposal writer where in the overall plan that passage belongs, which a plain similarity score alone cannot convey.

### 3.9 `app/tasks/`

**`app/tasks/__init__.py`** is a short docstring stating plainly that `library_indexing.py` is the live task module and `indexing.py` beside it is a tombstone, and flags a subtlety worth remembering: the tasks registered inside `library_indexing.py` deliberately keep the *old* `app.tasks.indexing.*` registered names rather than being renamed to match their new file location.

**`app/tasks/indexing.py`** is a tombstone, but its docstring is worth reading closely because it explains something a simpler tombstone would not need to: a Celery task's registered name (the string passed to `@celery_app.task(name=...)`) is the routing key carried inside every message a worker ever receives, entirely independent of which Python file that task's code happens to live in today. If the tasks had been renamed to match their new module path when they moved, any message already sitting in the Redis queue at deploy time (queued under the old name) would arrive at a worker that no longer has a task registered under that name, and would simply be rejected. So the *module* moved to `library_indexing.py`, but the *registered names* stayed exactly as they were, and this tombstone exists specifically to stop anyone from accidentally re-registering a second, competing set of tasks under those same names by importing this old file, since Celery's rule for a name collision is that the last registration to run wins, meaning which actual implementation processes a given job would end up depending on unpredictable import order.

**`app/tasks/library_indexing.py`** is the live Celery task implementing the whole LIB-UI-04/05 indexing pipeline, one task per document, which is what makes incremental training actually incremental: nothing in this file ever reads or rewrites another document's rows, so training one new asset never touches the rest of the library. `_advance` is the shared helper every stage calls: it writes the new stage, progress percentage and message onto the persisted `IndexJob` row, optionally mirrors that stage onto the parent `Document`'s `training_status` column (routed through the `JOB_STAGE_TO_DOCUMENT_STATUS` lookup table from `models/enums.py` so the two columns can never be set to disagreeing values), commits, and *then* publishes the same update over Redis. Doing both, in that order, is deliberate: the WebSocket carries live updates for whoever is watching right now, but a client that connects late or reloads mid-run reads the persisted row instead of simply missing whichever stage happened while nobody was looking. `_run_pipeline` walks Parsing (calling into `parsers.extract`, then the category-specific parser via `registry.parse`), Tagging (calling `metadata.extract`, carefully distinguishing what the uploader typed from what the parser itself already inferred from what the metadata module is allowed to overwrite), and Embedding (chunking the parsed sections, deleting this document's own previously-indexed chunks and rebuilding them in batches of 32 so a large document reports incremental progress rather than sitting silent through one giant embedding call). The re-indexing delete happens deliberately *after* a successful parse rather than at the very start of the run, specifically so that a parse failure on a re-training attempt leaves the previously-indexed version of the document intact and searchable rather than deleting it and then failing to replace it. `index_document` is registered with `max_retries=0`, and the reasoning given is that a parse failure is almost always a bad or unreadable file, not a transient problem, so a silent automatic Celery retry would just re-run expensive OCR three times over and confuse the progress display for no benefit; failures are recorded on the document for a human to see and explicitly re-trigger instead.

**`app/tasks/tender_pipeline.py`** is the largest single file in the backend and implements Stages 2 through 4 of the tender pipeline end to end: parsing, section-aware chunking, LLM extraction, evidence matching, marks reporting, and output-folder assembly, all inside one Celery task. Three things in this file are worth understanding deeply rather than skimming, because together they are the single best worked example in the codebase of a real production concurrency problem and its fix.

The first is the `run_generation` counter and `expected_generation` parameter. A `Tender` row can, in principle, be acted on by more than one thing at once: a worker that is still mid-stage on an old run, a user who just clicked Stop, and a user who then immediately clicked Retry, all touching the same row within moments of each other. Every write the pipeline makes to a tender row (`_advance`, called after every single stage) is expressed as an `UPDATE ... WHERE id = :id AND run_generation = :expected_generation`, checked and applied as one atomic database statement, never as a separate `SELECT` to check the value followed by a second `UPDATE` to write it (which would leave a race window between the two). `cancel_tender` and `reprocess_tender`, over in `routes/tenders.py`, both increment `run_generation` the instant a user acts, which means a worker's very next `_advance` call, whenever it happens to get around to it, finds its own generation no longer matches the row's current one, its `UPDATE` affects zero rows, and `_advance` raises `TenderCancelled` right there, cleanly stopping that specific stale worker without it ever needing to know *why* it was stopped or *what* superseded it. `run_tender_pipeline`'s own docstring explains why `expected_generation` is passed in explicitly at enqueue time rather than simply re-read from the row when the task starts running: a task can sit queued behind other work for a while, and if a second Reprocess bumped the counter again during that wait, a task that re-read the counter fresh at start time would wrongly believe it owned that newer generation too, and two tasks would race against each other as if they were the same run. Carrying the exact value the caller had in hand at enqueue time keeps every task permanently tied to the one specific attempt it actually represents, for its entire lifetime, no matter how long it waited in the queue first.

The second is `_fail`'s ordering, worth reading immediately after `_advance`. It calls `db.rollback()` before reading `tender.status`, specifically so that the failing stage's own half-committed work is discarded first and the in-memory `tender` object reflects the last stage that was actually, successfully committed, which is what makes `failed_stage` genuinely truthful rather than reporting whatever a half-applied update happened to leave behind. `_fail` is gated on the same `run_generation` check as `_advance`, for a subtle reason worth sitting with: `TenderCancelled` being raised means someone has already acted on this tender, but if that action was Stop immediately followed by Retry (rather than only Stop), a second, brand-new worker may already be running the new attempt by the time the first, stale worker's exception handler gets around to writing `FAILED`. Writing that unconditionally would clobber the new run's live, in-progress status the instant the old worker caught up, which is precisely the bug the whole generation guard exists to prevent, just relocated from the success path to the error path instead of being caught there too.

The third is `_run_matching`, `_compute_report`, and `_assemble_folder`'s shared, explicitly named "covered" rule, worth reading as a single unit even though it is defined three times: a match counts toward a requirement's coverage if a human has explicitly accepted it, or if it auto-matched (confidence at or above 0.85) and has not subsequently been rejected by a reviewer. `MATCH_TOP_K = 2`, `AUTO_MATCH_THRESHOLD = 0.85` and `SUGGESTED_MATCH_FLOOR = 0.60` carry an explicit comment recording that the floor and candidate count were tuned down from earlier values (a floor of 0.50 and a top-k of 5) specifically because every qualifying candidate becomes its own row a human has to click through, and the looser original settings were producing hundreds of low-value near-duplicate suggestions per tender. `_assemble_folder` writes a four-sheet Excel workbook (Requirements, Summary, Evidence Matches, Instructions) via `openpyxl`, using the tender's own verbatim wording in the `*_raw` fields wherever available rather than the normalized enum values, specifically so values like "No/Advisory" and "Financial / Pass-Fail" survive into the client-facing tracker exactly as the tender wrote them, and copies every accepted evidence file into a "Required Documents" subfolder before zipping the whole thing, rebuilding from scratch on every call (including on finalize) so that a reviewer rejecting a match and re-finalizing never leaves an orphaned, no-longer-relevant evidence file sitting in the package.

### 3.10 `requirements.txt` and `alembic.ini`

**`requirements.txt`** pins every dependency and its own header comment records a real decision worth understanding: the pins were taken from the fuller prototype rather than from the flat one, even though the flat prototype's own pins were individually newer across the board, because the flat prototype's package list was a strict subset that never included JWT handling, password hashing, email validation or the Anthropic client at all, none of which its stubbed-out authentication ever needed. Mixing the newer individual version numbers into the larger, real package set would mean shipping a specific combination of versions that had literally never been run together by anyone, which is a risk worth avoiding even when every individual version bump looks harmless in isolation; the comment states plainly that any future bump should happen deliberately, together with the test suite, rather than as an incidental side effect of copying a requirements file from somewhere else.

**`alembic.ini`** is Alembic's own configuration file and is notable mainly for what it deliberately leaves blank: `sqlalchemy.url` is empty, with a comment explaining that `alembic/env.py` overwrites it at runtime from `Settings.DATABASE_URL`, so the actual database connection string lives in exactly one place, the `.env` file, and is never duplicated into (or accidentally committed inside) a config file that would otherwise sit in version control.

## 4. Patterns worth reusing in your own projects

- **Ticket-based authentication for WebSockets.** A browser's WebSocket constructor cannot set an `Authorization` header, so putting a long-lived bearer token in the connection URL leaks it into browser history and proxy logs for as long as that token stays valid. Instead, mint a random, single-use, short-TTL ticket over an ordinary authenticated HTTP call, scope it to the exact resource the socket will connect to, and redeem it atomically (Redis `GETDEL`, not a `GET` followed by a `DELETE`) the moment the socket connects. This generalizes to any transport that cannot carry your normal credential.

- **Tombstone files instead of silent deletion during a merge.** When two versions of a module exist after combining codebases and only one is meant to run, do not simply delete the loser and trust that nobody references it from memory, and do not just leave it sitting there unused either. Replace its body with a clear docstring naming the live replacement and the concrete reason the old version cannot simply be revived, followed by a `raise ImportError(...)`. A stray import then fails loudly at the exact line that would otherwise have silently misconfigured the app, rather than failing mysteriously somewhere else, or worse, not failing at all.

- **A generation counter for cooperative cancellation.** When a long-running background job can be raced by a user action (stop, then immediately retry) or by itself (a stale worker still finishing while a newer attempt has already started), give the row a monotonically increasing counter. Bump it the instant the user acts, capture its value once when a worker task starts, thread that captured value through every subsequent write as part of the write's own `WHERE` clause, and treat a write that affects zero rows as "I have been superseded, stop." This is a general, robust pattern for cooperative cancellation of anything running outside the request/response cycle, and it does not depend on the worker ever being told explicitly that it was cancelled.

- **Two-tier model selection for cost.** Not every LLM call needs your most capable, most expensive model. Mechanical, high-volume, "extract this exact field verbatim" work (this backend's tender extraction, metadata tagging, and section classification) can run reliably on a cheap, fast model, while work that genuinely has to weigh evidence and write connected prose (a grounded question-answering feature) justifies a more expensive one. Make the model a named setting per call site rather than one single global model constant, so the tradeoff is a one-line configuration change rather than a code change.

- **Keep the request/response schema separate from the database schema.** A Pydantic (or equivalent) schema and an ORM model can look almost identical and still be doing two different jobs. Letting them diverge on purpose, rather than collapsing them into one class, is what lets your database evolve (new internal columns, a changed storage layout) without automatically changing your API, and lets your API evolve without forcing a migration.

- **Persist progress state, do not only stream it.** A WebSocket delivers events to whoever happens to be listening right now; it says nothing to a client that connects a minute late or reloads mid-run. Anywhere you stream progress, also write the latest snapshot somewhere durable (a database row, or a cache key with a sensible TTL) and always serve that snapshot first, before subscribing to new events, on every connection. Otherwise "reconnect" quietly becomes "start over from a blank screen."

- **Local, dependency-free defaults where they exist.** Choosing a locally-run embedding model instead of a second hosted API removed an entire external dependency (a second API key, a second point of failure, a second thing that can rate-limit you) at the cost of a one-time model download and some CPU time. When a capability genuinely can run locally without materially hurting quality, that is usually worth doing before reaching for another external service, especially one you would otherwise be adding purely to save a small amount of infrastructure.

- **A dedicated, narrow health check per external dependency.** A generic "is the process alive" health check tells you almost nothing about why a specific downstream integration (here, the LLM provider) is failing. A small endpoint that exercises the exact client, URL, and call shape your real code path uses, and reports the underlying error verbatim, turns a "why is this mysteriously broken" investigation into a five-second check, and is worth building for any external dependency your app cannot function without.

- **Write down why you removed something, not just that you removed it.** Several files in this codebase (the `ANTHROPIC_USER_AGENT` history in `core/config.py`, the OCR path fix in `pdf_extraction.py`, the tender-metadata `*_raw` columns) keep a short comment explaining a decision that is no longer visible in the code itself, specifically because the reasoning would otherwise be lost the moment the old code was deleted, and a future reader (including a future version of yourself) would have no way to know the removal was deliberate rather than an oversight waiting to be "fixed" back in.

- **Grep before you trust a docstring.** This backend has at least one service module (`support_email.py`) that is fully implemented, carefully documented, and describes a real feature, but is never actually called from any live code path; the feature it describes is implemented a different way entirely, on the frontend. A confident docstring is not proof that the code it describes runs. Before you rely on what a module says about itself, especially in a codebase you did not write, check who actually imports and calls it.
