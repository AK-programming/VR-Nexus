# VR-Nexus Frontend, Explained

This document walks through the frontend of VR-Nexus, a Tender Intelligence and Evidence Matching platform. The stack is React 19, Vite, TypeScript, React Router 7, and Tailwind CSS v4. The frontend talks to a FastAPI backend two ways: ordinary REST calls that go through a Vite dev proxy (so the browser only ever calls its own origin, no CORS needed), and two authenticated WebSocket connections that stream live progress for the tender-analysis pipeline and for evidence-library indexing jobs.

The request lifecycle, end to end, looks like this. The browser loads `index.html`, which pulls in `src/main.tsx`. `main.tsx` applies the saved theme before anything renders (so there is no flash of the wrong theme), fires off a background session-bootstrap check, and mounts `App.tsx`. `App.tsx` wraps the whole tree in `AppProviders` (currently just `BrowserRouter`) and renders `AppRouter`, which is the single route table in `src/app/router.tsx`. React Router matches the current URL against that table and picks a layout: `DashboardLayout` for anything inside the authenticated app, `AuthLayout` for the login and password screens. Inside the matched layout, a page component from `src/pages/` renders. That page component almost always uses a custom hook (`useAsyncData`, or the more specialized `useJobProgress` / `useTenderProgress`) to fetch its data. The hook calls a function in `src/services/`, which is a thin wrapper around `src/lib/apiClient.ts`, which does the actual `fetch()` call. Data that needs to be shared across unrelated parts of the tree (the signed-in user, the theme) lives in a Zustand store under `src/store/`, not in the page component. The page then renders a tree of components from `src/components/`, some of which (the two progress-tracking pages, `ProcessingPage` and `TenderProcessingPage`) open a WebSocket of their own via the progress hooks, so the browser gets pipeline updates pushed to it instead of having to poll.

One correction worth stating up front, because it is easy to assume otherwise from the phrase "React Router 7": this codebase does **not** use the newer data-router APIs (`createBrowserRouter`, loaders, actions). It uses the classic, component-based `<Routes>` / `<Route>` API wrapped in a plain `<BrowserRouter>`. Data fetching is done entirely in hooks inside components, not in router loaders. That is a legitimate, well-supported way to use React Router 7, and it is what this codebase actually does, so that is what this document describes.

## Core concepts for beginners

**A React component** is just a JavaScript (here, TypeScript) function that returns a description of some UI, written in JSX (HTML-looking syntax embedded in the function body). React calls that function again whenever the data it depends on changes, and efficiently patches the real DOM to match. `function Button({ children }) { return <button>{children}</button> }` is a complete, valid component. Everything in `src/pages/`, `src/components/`, and `src/Layout/` is a component like this, just larger.

**Hooks** are functions, always starting with `use`, that let a component "hook into" React features: `useState` for a piece of data that changes over time and should trigger a re-render when it does, `useEffect` for running code in response to a component appearing, updating, or being removed (side effects like subscriptions and network calls), `useRef` for a mutable value that does *not* trigger a re-render when it changes (a DOM node reference, or a value you need to remember across renders without re-rendering because of it). A **custom hook** is simply a function, also named `useSomething`, that calls React's built-in hooks internally and packages up some reusable piece of logic. This codebase writes three custom hooks worth understanding before reading anything else: `useAsyncData` (load some data, track loading/error/success, allow a refetch, keep the old data visible while a background refresh happens), `useJobProgress` and `useTenderProgress` (open a WebSocket, listen for progress frames, fall back to polling if the socket won't stay open). Writing these once and reusing them means every page that loads data behaves the same way under slow networks, errors, and cancelled navigations, instead of every page reinventing its own ad hoc loading state.

**React Router's nested layout routes** let one route render a shared shell and an inner `<Outlet />` where a child route's own component appears. VR-Nexus uses this three levels deep in places: `DashboardLayout` renders the sidebar, header, and footer for the entire authenticated app and puts an `<Outlet />` in the middle; `DocumentsLayout` (nested inside that) renders the "Library / Upload / Processing" tab bar for the Documents section and puts its own `<Outlet />` inside that; the actual `DocumentsOverviewPage`, `UploadDocumentsPage`, or `ProcessingPage` renders inside that innermost outlet. The payoff is that the sidebar and the tab bar are written once, not duplicated on every page, and swapping tabs does not remount the outer shell.

**A service module** is this codebase's name for a file in `src/services/` whose whole job is to know the shape of one backend resource's HTTP endpoints and expose plain async functions (`listTenders()`, `getTender(id)`, `uploadDocument(file)`) that return typed data. Nothing else in the app is allowed to call `fetch()` directly or know a URL path; components and hooks call a service function and get back a typed object or throw a typed `ApiError`. This is the layer that would need to change if the backend's routes moved, and it is the layer you read first to understand "what can this app actually do to the server."

**Zustand**, confirmed by `import { create } from 'zustand'` in `authStore.ts` and `themeStore.ts`, is a small state-management library for data that many unrelated components need to read or change: who is signed in, what the current theme is. A Zustand store is created once with `create<State>((set, get) => ({ ...initialState, someAction: () => set(...) }))` and any component can call the resulting hook, `useAuthStore((state) => state.user)`, to subscribe to just the slice of state it needs; only components that read a field that actually changed re-render. This is different from a component's own `useState`, which is private to that component and its children, and it is different from prop drilling, which is passing a value down through many layers of components that do not themselves need it. The rule of thumb in this codebase, and a good one generally, is: local state stays in the component (`useState`); state genuinely shared across the tree, or state that must persist across a page navigation without being refetched, goes in a store.

**TypeScript models** are the files in `src/models/`. They are not database models and they render nothing; they are type and constant definitions that describe the exact shape of data going over the wire to and from the FastAPI backend (mirroring its Pydantic schemas), plus a handful of pure helper functions for normalizing or classifying that data. The payoff of writing these out by hand is that a typo in a field name, or sending a field the backend does not expect, is caught at compile time in your editor, months before it would otherwise surface as a confusing runtime bug or a silent `undefined`.

**A guard, or protected-route, component** is a small wrapper component that renders its children only under some condition and redirects otherwise. `RequireAuth` wraps every authenticated route and redirects to `/login` if nobody is signed in; `RedirectIfAuthenticated` wraps the login and register pages and redirects *away* from them if someone already is signed in. Guards keep that check in one place instead of every page re-implementing "if not logged in, redirect."

**Why a WebSocket hook is separate from the REST service layer**: a normal HTTP request-response cycle is a poor fit for "tell me every few seconds how far along this multi-minute background job has gotten." A WebSocket is a single long-lived connection the server can push messages down at any time, which is the right primitive for progress updates. But WebSockets in the browser cannot carry an `Authorization` header the way `fetch()` can, connections can drop for reasons that have nothing to do with the job itself (a laptop sleeping, a flaky network), and the calling component still needs an ordinary hook-shaped API (`{ progress, status }`) rather than raw socket events. `useJobProgress` and `useTenderProgress` exist to absorb all of that: minting a short-lived auth ticket over HTTP first, opening the socket, parsing frames, falling back to polling the REST endpoint if the socket cannot be sustained, and cleaning up correctly when the component unmounts.

## File-by-file walkthrough

### Root configuration

**`package.json`** pins the dependency set: React 19.2.8 and react-dom 19.2.8, `react-router-dom` ^7.0.0, `zustand` ^5.0.2, `pdfjs-dist` pinned to the exact version `5.4.296` (not a caret range) alongside `react-pdf` ^10.1.0, `react-dropzone` ^14.3.8, `recharts` ^2.15.0, Tailwind ^4.0.0 with its `@tailwindcss/vite` plugin, Vite ^8.2.0, and TypeScript ^5.9.0. The `build` script runs `npm run typecheck` before `vite build`, so a type error fails the build rather than shipping. `pdfjs-dist` being pinned exactly, while everything else uses a caret range, is deliberate: `react-pdf` bundles a PDF.js "worker" script whose version must match the `pdfjs-dist` package's API version exactly, or PDF rendering breaks with a version-mismatch error at runtime, so this one dependency cannot float to whatever a caret range would resolve to.

**`vite.config.ts`** registers the React and Tailwind v4 Vite plugins (Tailwind v4 is configured as a Vite plugin here, not as a PostCSS plugin, so there is no `tailwind.config.js` or `postcss.config.js` anywhere in the project), sets up the `@` import alias to point at `./src` (matched by a corresponding `paths` entry in `tsconfig.app.json`), and configures the dev proxy: any request to `/api/*` is forwarded to `http://127.0.0.1:8000`, and any request to `/ws/*` is forwarded as a WebSocket to `ws://127.0.0.1:8000`. A comment in the file explains why `127.0.0.1` and not `localhost` is used for the proxy target: Node can resolve `localhost` to the IPv6 loopback address `::1`, and if the backend is only bound to the IPv4 loopback, that resolves to a connection refused error that has nothing to do with the actual proxy configuration being wrong.

**`index.html`** is a minimal Vite entry HTML file: an inline data-URI SVG favicon (a red hexagon, matching the brand badge used elsewhere in the UI, chosen specifically so the browser never makes a separate network request for a favicon file that might 404), Google Fonts preconnect and stylesheet links for Sora (used for headings and buttons, referenced from CSS as `--font-display`) and Inter (used for body text and inputs, `--font-sans`), a `<div id="root">`, and a single `<script type="module" src="/src/main.tsx">` that boots the app.

### `src/` root

**`src/App.tsx`** is intentionally trivial: it renders `<AppProviders><AppRouter /></AppProviders>` and nothing else. Keeping the true root this thin means there is exactly one obvious place to add a new app-wide wrapper later (a query client, a toast host) without touching routing logic.

**`src/main.tsx`** is the actual entry point. Before React ever renders anything, it calls `applyTheme(getStoredTheme())` synchronously, which reads the saved theme preference from `localStorage` and stamps the corresponding `data-theme` attribute onto `<html>`. Doing this before the first paint, rather than inside a React effect after mount, is what prevents a "flash of wrong theme": if it happened after mount, a dark-mode user would see a flash of the light theme for one frame on every load. Immediately after, it calls `void useAuthStore.getState().bootstrap()`, deliberately not awaited (the `void` operator marks that on purpose) and deliberately placed here rather than inside a `useEffect` in `App.tsx`. The reasoning, per the code's own comments, is that React's Strict Mode intentionally double-invokes effects in development to surface bugs, and a token-refresh call that runs twice in quick succession during bootstrap could race against itself; running it once, here, at true module-load time, sidesteps that.

**`src/vite-env.d.ts`** is a small ambient type declaration file. It narrows Vite's built-in `ImportMetaEnv` type (which otherwise allows any string key) to also specifically know about `VITE_API_BASE_URL?: string`, the one environment variable this app reads (and in development it is typically empty, since requests go through the dev proxy instead of an absolute URL).

**`src/index.css`** is where Tailwind v4's `@theme` directive defines the app's design tokens directly in CSS (a v4 feature; there is no separate JS theme config file). It sets `--font-display` (Sora) and `--font-sans` (Inter) with system-font fallback stacks, brand colors (`brand-500` is the signature red, `#e8151b`), a dark "ink" palette used for the sidebar, and semantic tokens like `surface`, `field`, and `hairline` that are defined once for light mode and then redefined under a `[data-theme='dark']` selector so the same class names (`bg-surface`, `border-hairline`) automatically look right in both themes. A `@custom-variant dark` directive ties Tailwind's `dark:` variant to that same `data-theme="dark"` attribute rather than Tailwind's default (which watches for a `.dark` class on `<html>`) or the OS-level `prefers-color-scheme` media query directly; this is what lets `theme.ts` implement an explicit light/dark/system toggle rather than being locked to the OS setting.

### `src/app/`

**`src/app/router.tsx`** is the single source of truth for every URL in the app, using the classic `<Routes>` / `<Route>` component tree (not `createBrowserRouter`). Public routes (`/login`, `/register`) are wrapped in `RedirectIfAuthenticated`; the forgot-password and reset-password routes are not gated at all, since a signed-in user might still need to reset a password. Every authenticated route is nested inside one `<Route element={<RequireAuth><DashboardLayout /></RequireAuth>}>` block. Inside that block, the Documents section and the Tender Analysis section are each further nested inside their own layout route (`DocumentsLayout`, `TenderAnalysisLayout`) so their index/upload/processing tabs share a tab bar. Detail and review pages for a specific tender or document (matched by an ID in the URL, using patterns like `TENDER_DETAIL_PATTERN`) are deliberately *not* nested as another tab inside the Tender Analysis layout; they sit as sibling routes directly under `DashboardLayout`. The reasoning given in the surrounding code is about not implying an affordance that does not exist: nesting them as a fourth tab would visually suggest you can tab away from a tender's review screen and tab back, when the actual navigation model is "open a specific tender, then go back to the list." A catch-all `<Route path="*">` redirects anything unmatched to `/login`.

**`src/app/providers.tsx`** exports `AppProviders`, which currently only wraps its children in `<BrowserRouter>`. A code comment marks it explicitly as the single place future app-wide providers (a data-fetching cache/query client, a toast notification host) should be added, so that `App.tsx` itself never needs to change shape again.

**`src/app/guards.tsx`** defines the two route guards. `RequireAuth` checks `isAuthenticated` from the auth store; if false, it renders `<Navigate to="/login" state={{ from: pathname + search }} />` so the login page can send the user back to where they were headed after they sign in. It optimistically trusts a session that was restored from storage before the backend has had a chance to verify the token is still valid, on the reasoning that showing the UI immediately (and letting a background 401 correct course if the token turns out to be stale) is a better experience than blocking on a network round trip on every navigation. `RedirectIfAuthenticated` is the mirror image for the login and register pages, but with an important asymmetry: it waits for `isBootstrapping` to become false before deciding whether to redirect, so a user with a genuinely valid stored session is not shown a flash of the login form while that session is still being verified. The file also exports `readReturnPath(state)`, a small guard function that only trusts a `from` path if it starts with a single `/` and not `//`, which blocks a crafted redirect URL from bouncing the user to an external site (an open-redirect vulnerability) after login.

**`src/constants/routes.ts`** defines the `ROUTES` object (an `as const` object of every static path in the app) plus, for the three routes that carry a dynamic ID in their URL, a matched pair of exports: a `_PATTERN` string for React Router to match against (e.g. `TENDER_DETAIL_PATTERN = '/tenders/:tenderId'`) and a builder function (`tenderDetailPath(id)`) that other code calls to construct an actual link, so no component ever hand-writes a template string for one of these URLs and risks a typo diverging from the route table.

### `src/lib/`

**`src/lib/apiClient.ts`** is the lowest layer of the network stack and the only file in the app that calls `fetch()` directly. It exports an `ApiError` class carrying a message, an HTTP status, an optional structured `detail` payload from the backend, and an `isOffline` flag; `readMessage()` is a small helper that unwraps FastAPI's several different error-body shapes (a plain string, a `{ detail: string }`, or a `{ detail: [...] }` validation-error array) into one consistent message. To avoid a circular import with `authStore.ts` (the client needs to read the current access token and needs to trigger a refresh on a 401, but the auth store needs to call the client to make its own requests), the file exposes two injection seams, `setAuthTokenProvider(fn)` and `setUnauthorizedHandler(fn)`, which `authStore.ts` calls once at its own module load time to hand the client a getter and a callback. `refreshOnce()` implements a single-flight pattern: if several requests hit a 401 at nearly the same moment, only the first triggers an actual token refresh, and the rest await that same in-flight promise instead of each firing their own redundant refresh call. The core `request<T>()` function does the actual fetch, retries exactly once on a 401 (guarded by an `isRetry` parameter so a second failure does not loop forever), and the exported `api` object exposes the verbs the rest of the app calls: `get`, `getBlob` (for binary responses like PDFs), `postJson`, `postForm`, `postEmpty`, `patchJson`, `delete`. `websocketUrl(path)` builds a `ws://` or `wss://` URL from a relative path (matching the protocol of the current page), and `errorMessage(error)` is a small safe extractor used throughout the UI to turn any caught error into a displayable string.

**`src/lib/formatting.ts`** collects small, pure display-formatting functions so the same date or number never gets formatted two different ways in two different components. `formatShortDate` / `formatLongDate` deliberately use a fixed day-month-year (en-GB) format rather than letting the browser's locale decide, because the product's audience is Pakistani and a locale-auto format would silently flip to month-day-year for a US-locale browser. `formatRelativeTime` ("just now", "5 min ago", "2 days ago") is hand-written rather than using the built-in `Intl.RelativeTimeFormat`, again for consistent wording across browsers. `formatBytes` and `formatGigabytes` handle file-size display (1024-based; kilobytes and plain bytes show no decimal place, megabytes and gigabytes show one). `formatCount`, `formatSignedPercent`, `formatInitials`, `formatRole`, and `formatFirstName` round out small display needs used across the dashboard and account screens.

**`src/lib/theme.ts`** defines the `Theme = 'light' | 'dark' | 'system'` type, `getStoredTheme` / `storeTheme` (both wrapped in `try`/`catch` since `localStorage` can throw in some private-browsing contexts), `prefersDark()` (reads the OS-level media query), `resolveTheme()` (turns `'system'` into a concrete `'light'` or `'dark'` by checking `prefersDark()`), and `applyTheme()`, which stamps the resolved theme onto `<html data-theme="...">` and also sets the native `colorScheme` CSS property so browser-drawn UI (scrollbars, form controls) matches too.

**`src/lib/validation.ts`** holds the client-side form-validation functions: `validateName`, `validateEmail` (a deliberately loose regex, on the stated principle that the server is the actual authority on what counts as a valid email, and the client check exists only to catch obvious typos before a round trip), `validateNewPassword` (which measures length in *bytes*, using `TextEncoder`, not characters, because the backend hashes passwords with bcrypt and bcrypt silently truncates at 72 bytes; a password with multi-byte Unicode characters could pass a character-count check but still exceed the real byte limit, so the error message distinguishes the two), `validatePasswordPresent`, `validateConfirmPassword`, `validateOptionalPhone`, and `measurePasswordStrength` (a 0 to 4 score used only to show feedback to the user, not to block form submission).

**`src/lib/pdfWorker.ts`** does the one-time setup `react-pdf` needs: it points `pdfjs.GlobalWorkerOptions.workerSrc` at the PDF.js worker script using `new URL('pdfjs-dist/build/pdf.worker.min.mjs', import.meta.url)` (a pattern Vite understands and bundles correctly), imports the `AnnotationLayer.css` and `TextLayer.css` stylesheets PDF.js needs for text selection and link overlays to render correctly, and exports a constant `PDF_OPTIONS = { isEvalSupported: false }`. That options object has to be declared once at module scope rather than written inline where it is used, because `react-pdf` compares the `options` prop it receives by object identity between renders; a fresh object literal on every render would look like a "new" options value each time and cause the PDF to be needlessly reloaded.

### `src/models/`

These files hold no rendering logic. They are the TypeScript description of exactly what the backend sends and expects, plus small pure functions for normalizing or deriving values from that data.

**`src/models/index.ts`** is a barrel file: `export * from './auth'`, so other files can import auth-related types from `@/models` instead of reaching into `@/models/auth` directly. (Notably, the other model files, `dashboard.ts`, `documents.ts`, `tenders.ts`, are imported directly by their own paths elsewhere in the app rather than being re-exported from this barrel.)

**`src/models/auth.ts`** defines `USER_ROLES` and the derived `UserRole` union type (as a readonly array plus `typeof USER_ROLES[number]`, rather than a TypeScript `enum`; see the closing patterns section for why), field-limit constants that mirror backend validation exactly (`NAME_MAX_LENGTH = 255`, `PASSWORD_MIN_LENGTH = 8`, `PASSWORD_MAX_LENGTH = 72` matching bcrypt's byte limit, `PHONE_MAX_LENGTH = 32`, `COMPANY_MAX_LENGTH = 255`), `normalizeUserRole` and `normalizeUser` (which defend against a role coming back from the server in unexpected casing or an unrecognized value by defaulting to the least-privileged role, `'user'`, rather than trusting unknown input), the wire request/response types `LoginRequest`, `RegisterRequest`, `RefreshRequest`, `ForgotPasswordRequest`, `ResetPasswordRequest`, `MessageResponse`, `User`, `TokenResponse`, the form-only types `LoginFormValues` and `RegisterFormValues`, the converters `toRegisterRequest` / `toLoginRequest` (which trim whitespace and convert blank optional fields to `null` before sending), `AuthSession`, and `AuthErrorKind` (a union of `invalid | expired | locked | disabled | conflict | validation | offline | unknown`) with its companion `AuthFailure` type, which is what lets `AuthAlert.tsx` show a different icon and message for "wrong password" versus "account locked" versus "you're offline" instead of one generic error string.

**`src/models/dashboard.ts`** is different in kind from the other model files: everything in it is a UI-only type, not a wire type, because there is no single dashboard endpoint on the backend. `SummaryStat`, `Project` / `ProjectStatus`, `ActivityEntry` / `ActivityKind`, `AnalysisPoint` / `AnalysisRange`, `StorageUsage`, `AssistantSuggestion`, `QuickAction`, and the aggregate `DashboardData` describe the shapes `DashboardPage.tsx` assembles on the client by combining data from the tender and document services.

**`src/models/documents.ts`** is the largest model file and mirrors the evidence-library backend closely. `DOCUMENT_CATEGORIES` and `CATEGORY_LABELS` define the fixed set of document categories and their display names; `DOCUMENT_FILE_TYPES` and `DROPZONE_ACCEPT` map accepted MIME types to file extensions for the upload dropzone, matched to what the server will actually accept, and `MAX_UPLOAD_MB = 100` caps upload size client-side before a wasted round trip. `fileTypeFromName()` infers a file's type from its extension. `TRAINING_STATUSES` enumerates a document's indexing lifecycle (`queued`, `parsing`, `tagging`, `embedding`, `indexed`, `failed`); `IN_FLIGHT_STATUSES` and `isInFlight()` identify the subset that means "still working." `JOB_STAGES`, `STAGE_LABELS`, and `STAGE_SEQUENCE` describe the five real processing stages a job walks through in order (`failed` is deliberately excluded from `STAGE_SEQUENCE`, since it is an outcome that can interrupt any stage, not a stage of its own); `stageStates()` and `isTerminalStage()` derive per-stage UI state (done / active / pending / failed) from a job's current status, which is what `ProcessingTimeline.tsx` renders directly. The wire types `LibraryDocument`, `DocumentChunk`, `LibraryDocumentDetail`, `IndexJob`, and `ProgressEvent` describe what the backend actually returns. `DuplicateMatch` / `DuplicateCheckResult` and `UploadResponse` / `TrainResponse` cover the upload flow. `CategoryCounts`, `LibraryStats`, `StatsRollup`, and `rollUpStats()` support the summary tiles on the library overview page. `UploadMetadata`, `EMPTY_UPLOAD_METADATA`, and `toUploadFormData()` describe the metadata form fields attached to an upload; the field names in `toUploadFormData()` are pinned using a `keyof` constraint against the request type, so a renamed backend field would fail to compile here rather than silently sending the old field name forever. A comment block in the file explicitly documents which fields are deliberately *not* modeled (`size_bytes`, `uploaded_by_name`, `summary`, `file_url`) and why, which is a genuinely useful habit: it tells the next reader that an omission was a decision, not an oversight. `PendingUpload` models an in-progress upload queue item; `documentTitle()`, `METADATA_FIELDS`, and `metadataTags()` are small display helpers; `LibrarySearchHit`, `LibrarySearchResponse`, and `LibraryAnswer` describe the search and ask (RAG) endpoint responses used by `AiAssistantPage`.

**`src/models/tenders.ts`** mirrors the tender-analysis pipeline. `TENDER_STATUSES` lists all eleven possible statuses (nine pipeline stages plus the two terminal outcomes `finalized` and `failed`); `PIPELINE_STAGES` is the nine in-flight ones. `TENDER_STATUS_LABELS`, `STAGE_LABELS`, and `STAGE_DESCRIPTIONS` supply display text. `IN_FLIGHT_STATUSES`, `isInFlight`, `isSocketTerminal`, and `isSettled` classify a status for UI purposes; notably, `isSocketTerminal` treats `ready_for_review` as *not* terminal for the WebSocket, since the socket in `useTenderProgress` deliberately stays open through the human review stage, only closing at `finalized` or `failed`. `stageStates()` mirrors the equivalent function in `documents.ts` for `TenderTimeline.tsx`. `REQUIREMENT_STATUSES` and `EVALUATION_IMPACTS` describe how an extracted requirement is classified after evidence matching; `requirementPriority()` derives a display priority from that. `MATCH_TYPES` encodes the three-way bucketing of an evidence match by its similarity score: `auto` for a similarity of 0.85 or above, `suggested` for 0.50 to 0.84, `missing` below 0.50. `MATCH_REVIEW_STATUSES`, `MatchReviewAction`, and `MatchReviewUpdate` support the human-in-the-loop review workflow. The wire types `TenderUploadResponse`, `TenderListItem`, `TenderDetail`, `TenderUpdate`, `Requirement`, `EvidenceMatch`, `ImpactBreakdown`, `TenderReport`, and `TenderChunk` describe the backend's responses; `TenderProgressFrame` / `TenderProgress` and their normalizers `progressFromFrame()` / `progressFromDetail()` let the progress hook and a plain REST-loaded tender detail both be converted into the same shape for the timeline component to render, regardless of which source the data came from. `TENDER_DROPZONE_ACCEPT` narrows the tender upload dropzone to PDF only, unlike the library dropzone's broader accept list. `TenderUploadMetadata`, `EMPTY_TENDER_METADATA`, `tenderTitle()`, and `hasReviewableAnalysis()` finish out the file.

### `src/store/`

**`src/store/authStorage.ts`** is a small, hand-rolled persistence helper, deliberately not using Zustand's built-in `persist` middleware. The reason is the "Remember me" checkbox on login: whether a session should survive a browser restart (`localStorage`) or only last the current tab session (`sessionStorage`) is a choice made dynamically at sign-in time, and `persist` is built around one fixed storage backend configured up front, not a per-login choice between two. `StoredSession` and `RestoredSession` are the relevant types; `isStoredSession()` is a runtime type guard that validates whatever comes back out of storage before trusting it (since storage content is not something TypeScript's compile-time types can actually guarantee, a user or a bug could have put anything there). `readStoredSession()` checks `sessionStorage` first and falls back to `localStorage`; `writeStoredSession()` writes to the correct one for the current "remember me" choice and explicitly clears the other, so a session cannot end up duplicated in both; `clearStoredSession()` wipes both on logout.

**`src/store/authStore.ts`** is the confirmed Zustand store for authentication (`import { create } from 'zustand'`). Its state includes `user`, `accessToken`, `refreshToken`, `remember`, `isSubmitting`, `isBootstrapping`, `failure`, and `notice`; its actions are `login`, `register`, `logout`, `refreshSession`, `bootstrap`, `clearFailure`, `clearNotice`, and `setNotice`. At module load time (outside the `create()` call, so it runs exactly once when the module first imports), it calls `readStoredSession()` to seed the store's initial state, which is what lets `RequireAuth` optimistically trust a restored session before any network round trip confirms it is still valid. `SESSION_EXPIRED` is a constant `AuthFailure` value reused wherever an expired session needs to be reported consistently. At the bottom of the file, `setAuthTokenProvider(() => useAuthStore.getState().accessToken)` and `setUnauthorizedHandler(() => useAuthStore.getState().refreshSession())` are called to plug this store into `apiClient.ts`'s injection seams, which is the resolution of the circular-dependency problem described under `apiClient.ts` above. The file also exports two selector functions, `selectIsAuthenticated` and `selectIsAdmin`, meant to be passed into `useAuthStore(selector)` calls elsewhere so that a component subscribes to exactly the derived boolean it needs rather than the whole user object.

**`src/store/themeStore.ts`** is the second, much smaller Zustand store. `ThemeState` holds `theme` (the user's stated preference: light, dark, or system), `resolved` (the concrete light-or-dark value actually applied), and a `setTheme` action that does three things in one call: persists the new choice via `storeTheme()`, applies it to the DOM via `applyTheme()`, and updates the store's own state so subscribed components (like the theme toggle button) reflect the new active state. A module-level `matchMedia('(prefers-color-scheme: dark)').addEventListener('change', ...)` listener re-invokes `setTheme('system')` whenever the OS-level preference changes, but only takes effect if the user's stored preference is currently `'system'`; a user who has explicitly chosen light or dark is not overridden by an OS change.

### `src/hooks/`

**`src/hooks/useAsyncData.ts`** is the general-purpose data-fetching hook used by nearly every page in the app. Called as `useAsyncData(fetcher, deps)`, it returns `{ status, data, error, offline, notFound, isRefreshing, refetch }`. Internally it creates a fresh `AbortController` for each run and aborts the previous one if the dependencies change or the component unmounts before a request finishes, which prevents a slow, stale response from a previous navigation overwriting fresher state. It keeps the `fetcher` function in a `ref` rather than a plain closure so that passing a new (but logically identical) function on every render does not re-trigger the effect; only the `deps` array controls when a refetch happens, plus an internal `reloadToken` counter that `refetch()` bumps to force a rerun on demand. It distinguishes a true first load (blank state, shows a loading skeleton) from a refetch of already-loaded data (keeps the previous data visible and sets `isRefreshing` instead of clearing the screen), and if a refetch fails, it keeps the stale data on screen rather than replacing a working view with an error, while still surfacing the error and an `offline` flag for the caller to show as a banner.

**`src/hooks/useJobProgress.ts`** tracks one library-document indexing job over its lifetime, cycling through the states `idle`, `live`, `polling`, `offline`, and `closed`. It first calls `mintJobWsTicket()` (an HTTP POST that returns a short-lived, single-use ticket, since the WebSocket handshake itself cannot carry an `Authorization` header), then opens the socket at `jobProgressUrl(jobId, ticket)`. It filters out ping frames and a distinct error-frame shape the server sends. If the socket fails three times in a row, it gives up on the socket and falls back to polling `getJob()` every two seconds instead, so a job's progress is never permanently stuck just because a WebSocket connection would not stay open (a corporate proxy blocking WebSocket upgrades, for instance). It tracks `lastRealStage` separately so that if a failure frame arrives without its own stage information, the UI can still correctly attribute the failure to whichever stage was last actually in progress. On cleanup, it explicitly nulls out the socket's event handlers before calling `.close()`, because closing a socket fires its own `onclose` handler, and without nulling the handlers first, that teardown-triggered `onclose` would itself try to start a new polling fallback right as the component is unmounting.

**`src/hooks/useTenderProgress.ts`** is the sibling hook for the tender-analysis pipeline, sharing the same overall shape (`idle` / `live` / `polling` / `offline` / `closed`) and the same ticket-then-socket pattern, but with different termination rules suited to a pipeline that includes a human review step: `ready_for_review` is explicitly *not* treated as socket-terminal, so the connection stays open through the review stage (in case, for example, a re-analysis is triggered while the review screen is still open); the true terminal states are only `finalized` and `failed`. This socket also does not receive ping frames the way the job-progress socket does, a small but real protocol difference between the two backend endpoints that the hook accounts for.

### `src/services/`

**`src/services/authService.ts`** defines `AUTH_ENDPOINTS`, an object of the auth API's URL paths, and exposes `authService.login`, `register`, `refresh`, `me`, `forgotPassword`, and `resetPassword`, each a thin async wrapper around a call to `api` from `apiClient.ts`. Every response that carries a user object is passed through `normalizeUser()` from the models layer before being returned, so a defensively-normalized user is the only shape the rest of the app ever sees. `classifyAuthError()` maps an `ApiError`'s HTTP status code onto one of the `AuthErrorKind` values, which is what lets the login form show "your account is locked" instead of a generic "request failed."

**`src/services/documentService.ts`** covers the evidence library. Reads: `listDocuments`, `getDocument`, `getStats`, `listStages`. Uploading: `uploadDocument`, `checkDuplicate`. Indexing: `train`, `retrainDocument`, `getJob`, `listDocumentJobs`, `deleteDocument`. `listProcessingQueue()` is a composed read with no single matching backend endpoint: it fans out five separately-filtered calls to `listDocuments` plus a `listDocumentJobs` call per document, capped at a `QUEUE_LIMIT` of 60 documents, to assemble the "what's currently processing" view. `mintJobWsTicket` and `jobProgressUrl` support the ticket-based WebSocket handshake described above. `documentImageUrl` and `documentFileUrl` build the raw backend path to a document's rendered page image or original file, but those paths are not directly usable in a plain `<img src="...">` or `<a href="...">`, since those requests would go out without an auth header; `fetchDocumentFileObjectUrl`, `fetchDocumentImageObjectUrl`, and `releaseObjectUrl` are the actual mechanism used, fetching the binary through the authenticated `api.getBlob()` call and turning the result into a `URL.createObjectURL()` object URL that a normal `<img>` or `<a>` tag can then point to, with `releaseObjectUrl` freeing the memory once it is no longer needed. `searchLibrary` and `askLibrary` call the retrieval and RAG-answer endpoints used by `AiAssistantPage`.

**`src/services/tenderService.ts`** mirrors `documentService.ts`'s structure for tenders. Reading: `listTenders`, `getTender`, `listRequirements`, `listMatches`, `getReport`. Uploading: `uploadTender` (a single-file, file-only request body, unlike the library upload which also carries metadata fields). Editing and review: `updateTender`, `reviewMatch`, `finalizeTender`, `cancelTender`, `reportTenderIssue`, `deleteTender`, `reprocessTender`. `mintTenderWsTicket` and `tenderProgressUrl` are the tender-side equivalents of the job-progress ticket functions. `tenderFileUrl` and `tenderDownloadUrl` are raw path builders; `fetchTenderFileObjectUrl`, `fetchTenderOutputObjectUrl`, and `releaseObjectUrl` are the authenticated-blob-to-object-URL functions used to actually display or download a tender's source PDF or its generated output document.

## Patterns worth reusing

- **Give network code exactly one entry point.** Every fetch in this app funnels through `apiClient.ts`. That is the only file that knows what an `Authorization` header looks like, how a 401 gets retried, and how FastAPI's several error-body shapes get unwrapped into one message. Any full-stack React project benefits from this: it means auth, retry, and error-shape logic only has to be written, tested, and fixed once.

- **Separate the "what can I ask the server" layer from the "how do I fetch" layer.** Services (`documentService.ts`, `tenderService.ts`) know endpoint paths and request/response shapes; `apiClient.ts` knows how to make an HTTP request. Neither knows about the other's concerns. This split is what makes it possible to change how requests are made (say, adding request deduplication) without touching a single page component.

- **Model the wire contract in code, by hand, even when it is tedious.** The files in `models/` are not glamorous, but a renamed backend field becomes a compile error here instead of a silent bug discovered by a user. Writing out `keyof`-constrained field lists like `toUploadFormData()` does is a small extra step that turns a whole category of "the form sends the wrong field name" bugs into something the compiler catches before the code ever runs.

- **Prefer `as const` arrays plus derived union types over TypeScript `enum`.** This codebase's `tsconfig` sets `erasableSyntaxOnly`, which forbids real TypeScript enums because, unlike almost every other TypeScript construct, an enum actually emits runtime JavaScript code that cannot be stripped by a type-erasure-only transpile step. The `USER_ROLES = ['admin', 'user'] as const` plus `type UserRole = typeof USER_ROLES[number]` pattern used throughout `models/` gets the same compile-time safety, is erasable, and additionally gives you a real runtime array you can iterate over (to build a `<select>`'s options, for instance) for free.

- **Break a circular dependency with a small injection seam, instead of merging the two modules together.** `apiClient.ts` needs to read the current access token; `authStore.ts` needs to make API calls. Rather than combining them into one large file, `apiClient.ts` exposes `setAuthTokenProvider()` and `setUnauthorizedHandler()`, and `authStore.ts` calls those once at its own module load. Each file stays focused on one responsibility and the dependency direction is explicit and one-directional at runtime, even though logically the two do depend on each other.

- **Design custom hooks around a state machine you can name, not just a loading boolean.** `useAsyncData` does not just track `isLoading`; it distinguishes a genuine first load from a background refresh, and it keeps stale data visible across a failed refresh rather than clobbering a working screen. `useJobProgress` and `useTenderProgress` both model an explicit `idle / live / polling / offline / closed` state rather than a single `connected` boolean. Naming the actual states a piece of async UI can be in, up front, tends to produce a hook that handles the edge cases (a slow network, a dropped socket, a cancelled navigation) correctly, rather than discovering them one bug report at a time.

- **A short-lived, single-use ticket is the standard way to authenticate a WebSocket.** Browsers cannot attach custom headers to a WebSocket handshake, so this app authenticates its normal REST calls with a bearer token but authenticates each WebSocket connection with a ticket minted, over an already-authenticated HTTP call, specifically for that one connection and expiring quickly. This pattern generalizes to any browser app that needs an authenticated long-lived connection (WebSocket or Server-Sent Events).

- **Binary, authenticated resources need the object-URL pattern, not a plain `src` or `href`.** Nothing in the browser lets a plain `<img src>`, `<a href>`, or a third-party library's `file` prop attach an `Authorization` header. This codebase's consistent answer is: fetch the resource through the authenticated API client as a blob, turn it into a `URL.createObjectURL()` object URL, hand that object URL to the `<img>` or `<a>` or `react-pdf`, and call `URL.revokeObjectURL()` when it is no longer needed to release the memory. Any app serving private images, PDFs, or downloads behind auth needs this same pattern.

- **A settings screen, or any screen, should not contain a control that does nothing.** `SettingsPage.tsx` states this outright: every toggle on it actually works, and features without a backend yet are left off the page entirely rather than shipped as inert placeholders. This is a small discipline that is easy to skip under deadline pressure and worth deliberately holding onto.

- **Reach for a native browser element before reaching for a library.** `ConfirmDialog.tsx` and `ReassignDialog.tsx` both use the plain `<dialog>` element with its `.showModal()` method rather than a modal library or a hand-rolled focus-trap implementation, and get a focus trap, Escape-to-close, an inert background, and top-layer stacking correct, for free, from the browser itself. The same instinct shows up in `icons.tsx` (hand-drawn SVGs instead of an icon library dependency) and in the choice to keep routing on plain `<Routes>`/`<Route>` rather than adopting a heavier data-router pattern the app does not actually need. Fewer dependencies means fewer version upgrades to manage and fewer surprises from a library's own internal behavior.
